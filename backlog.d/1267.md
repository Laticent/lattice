# studio(panel): cover the free-form panels' inputs, then gate it so a new one can't ship under the keyboard

## Summary

Second half of the keyboard-overlap work. #1266 unifies the *row* primitive, which covers every panel that has one. Four Studio panels have **no row primitive at all** — bare `<input>` in free-form layout — plus a scrolling body, which is exactly the shape that puts a field under the keyboard.

Then add the gate, so the next input added anywhere in the Studio can't ship broken silently.

## What's uncovered, and why a shared row won't reach it

| panel | scrolls? | text inputs | markup |
|---|---|---|---|
| Fabricate | yes | 10 | bare `<input>` (`:553`, `:573`, `:585`) |
| MotionStudio | yes | 10 | bare `<input>` (`:382`, `:415`, `:455`) |
| FinishStudio | yes | 4 | bare `<input>` (`:224`, `:242`, `:368`) |
| TtsSettings | yes | 3 | bare `<input>` (`:178`, `:255`) |
| SlideComments | no | 1 | bare `<textarea>` (`:45`) |
| WorkspaceSheet · AcronymEditor · LexiconEditor | no | 1–7 | bare inputs |

None defines a `Row`/`Field`, so #1266's primitive has nothing to slot into. The four that **scroll** are the live risk; the rest are latent — safe only because their bodies happen not to scroll today, which is not a property anyone is maintaining on purpose.

## Candidate mechanisms (pick during the work, not now)

1. **Put the pin on the input's own wrapper** rather than on a row — `PINNED_FIELD_ROW` is a class, so any element that owns a focused `<input>` can carry it. Cheapest, no redesign, but it needs each site touched.
2. **Adopt #1266's row where the shape genuinely fits** (TtsSettings and FinishStudio look closest to label-left/control-right) and use (1) for the rest.
3. **Accept a subset as out of scope** where the panel is a full-height form you'd expect to scroll anyway (Fabricate's and MotionStudio's prompt boxes may read fine already) — but decide that from a device check, not from a guess.

Whichever wins, the decision belongs in the note, because the reason the first two attempts at this problem failed was reasoning about it instead of measuring it.

## ★ Acceptance check — the gate is the point

A `check-ownership.js` check, in the established `SANCTIONED_*` idiom (mirroring HARD RULE #22's `checkPreviewHtmlSinks`):

- enumerate every text input (`<Input`, `<input`, `<Textarea`, `<textarea`, excluding `type=checkbox|radio|button|submit|reset|range|color|file|image`) under `docs/src/components/studio/**`;
- **each one must be** inside a pinning row, inside a `PanelDock`, or listed in `SANCTIONED_UNPINNED_INPUTS` with a written reason;
- **fail on an unlisted input AND on a stale entry**, so the list can't rot.

That is what makes "add a new input" safe: not that every input is pinned, but that adding an unpinned one is a build failure rather than a device-only surprise.

**Sequencing matters:** the gate lands *after* coverage. Added first it fails immediately against a large allowlist, which teaches nobody anything.

## Why this is `priority:low` while #1266 is medium

The uncovered panels are AI/authoring surfaces reached less often than Deck setup, and no defect has been reported in them. #1266 closes a *reported-shape* defect one tap from the one that was reported. This card closes the class of it.
