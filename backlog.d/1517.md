# [Bug] Closing the add-slide gallery leaves ~70 documents (~380MB) resident

## Summary

Closing the Studio's add-slide gallery does not promptly hand back the memory its thumbnails allocated. Measured with forced GC, ~70 documents and a few hundred MB stay resident with only the one live preview left in the page.

## Swimlane

`engineering/decisions/2026-08-10-thumbnail-window-is-two-way.md` § 6 "Logged, not fixed" — found while fixing #1463, off the path of that change, so it was recorded rather than pulled into that diff (HARD RULE #18).

## Done when

With the same harness as #1463 (Playwright + CDP `Performance.getMetrics`, `HeapProfiler.collectGarbage` twice before each read), open the gallery, scroll it top to bottom, close it: `Documents` returns close to its pre-open value (~26 at the top of the grid, ~4 at Studio load) rather than staying near its scrolled peak, and Chrome RSS drops correspondingly. A regression oracle in `docs/e2e/gallery-preview-budget.spec.ts` asserting the post-close live/document count.

## What was measured

Built site, desktop 1440×900, GC forced before every read. Five open-scroll-close cycles:

| | before #1463 | after #1463 |
|---|---|---|
| Studio loaded | 4 docs / 917MB RSS | 4 docs / 917MB |
| gallery open, top of grid | 26 docs / ~1059MB | 26 docs / ~1047MB |
| after close (cycles 1–5) | **129 docs / ~1.5GB** | **71 docs / ~1.31GB** |

## Why this is medium, not high

It is **flat across all five cycles** in both versions — a steady-state residue, not a leak, and not what crashed the tab in #1463 (that was the scroll itself, now capped). The cost is that a user who opens the gallery once keeps a few hundred MB allocated for the rest of the session.

## Where to start

`DeckPreview`'s unmount cleanup calls `renderer.dispose()` and React removes the `<figure>`, so the obvious roots are already released (`single-slide-render.ts` `dispose()`: `scaleTargets`, `ownedObservers`, theme observers, timers, intervals). Something else is holding the detached documents — worth a heap snapshot with retainer paths rather than more code reading.

## Note on measuring this

An **unforced** `Documents` read is not evidence: it counts detached documents until they are collected, so it reports the collection backlog rather than what is retained. During the #1463 work an unforced read made a working fix look like a regression (606 documents / 2.8GB). Force GC twice with a beat between, before every read.
