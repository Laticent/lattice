# Spike: let the pre-paint skeletons wrap the real components instead of hand-mirroring them

## Summary

The Studio's pre-paint shell is built in **three tiers**, and only two of them are safe.

1. **Real shared components** — `chrome-parts.tsx` exports `PostureDial`, `BarIcon` and `EditorSkeleton`, imported by *both* `StudioShell` and `StudioChromeSkeleton`. The topbar dial and the phone's eight-cell bar are the app's own components, rendered at build time with no-op handlers.
2. **Hand-mirrored markup** — the preview sub-bar, the slide navigator and the deck status strip are re-typed copies of the app's inline JSX: padding, text classes, borders and container queries, all duplicated by hand.
3. **Neutral content** — `ContentBar` where per-deck values would go, because the shell genuinely cannot know slide names or counts.

This spike asks whether **tier 2 should exist at all** — whether those rows can instead render the *real* component with its content masked, which is how most skeleton implementations work.

**The evidence that this is worth asking.** #1512 fixed five defects in the shell. Every one of them lived in tier 2, and every one is impossible under the wrapping model:

| Defect | Why it existed |
|---|---|
| Lens trigger `px-2.5 py-1` vs the app's `px-3 py-1.5 text-[12.5px]` | the skeleton hand-drew a control instead of using the real one |
| Slide counter `px-2.5 py-1.5` vs the app's `px-2 py-0.5` | same |
| A duplicated `border-t` on the navigator row | hand-drawn container |
| `ContentBar` had no line box, so no row could track font size | a fake placeholder has no text metrics; real text does |
| The `@[21rem]` container query had to be hand-mirrored | the real component already carries it |

Five for five. The hand-mirror is duplication with no upside — it exists because those rows were never converted, not because mirroring is right.

## Swimlane

`engineering/decisions/2026-08-09-shell-bands-text-metrics.md` — the #1496 fix, which found and repaired all five tier-2 defects and records the mechanism (a flex container has no strut, so only a child containing real text can track font size).

Prior art for the pattern being proposed: `engineering/decisions/2026-08-09-studio-shell-structural-completeness.md` (#1444), which created `chrome-parts.tsx` and converted the topbar and action bar — and whose claim *"no px constant and no copied SVG survive in the shell"* is true of the topbar but was **never true of the pane rows**. Part of why this stayed invisible.

Constraint that must not be broken: `engineering/decisions/2026-07-21-studio-preview-one-skeleton.md` — the shell must never paint per-deck content (slide names, counts, palette). A second content surface that disagrees with the live one is worse than no content.

## Done when

A spike branch that converts **one** row end to end — the **deck status strip**, the simplest of the three — and a written recommendation on whether to convert the other two.

Concretely, all of:

1. The status strip is a presentational component in `chrome-parts.tsx`, taking props, imported by **both** `StudioShell` and `StudioChromeSkeleton`. No padding, text-size, border or container-query value for that row is typed twice anywhere.
2. It renders at **build time with zero client JS** (Astro renders it with no client directive), so the shell still ships markup only.
3. A masking primitive keeps text metrics intact: the masked row's measured height matches the app's to ≤1px at default, 18px and 24px minimum font size. `color: transparent` over a painted bar is the candidate — real glyphs, so the line box is real.
4. `npm run test:e2e -- studio-instant-shell.spec.ts studio-shell-parity.spec.ts` is green on `desktop`, `mobile` **and** `minfont` — currently 46 cases. The default case must stay **0px on every band**; that is the no-regression bar and it is a test run, not a judgement.
5. The recommendation states explicitly whether the phantom-control risk below materialised, with evidence either way.
