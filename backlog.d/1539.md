# SLICE_CACHE_MAX (24) sits below PREVIEW_BUDGET (32), so a long overview traversal outruns the cache that makes recycling cheap

## Summary

`SLICE_CACHE_MAX = 24` (`docs/src/lib/single-slide-render.ts`) is smaller than `PREVIEW_BUDGET = 32` (`docs/src/components/studio/slide-thumb.tsx`). The mounted working set is therefore strictly larger than the LRU cache that is supposed to make a recycled tile cheap to bring back, so on a deck longer than 24 slides a returning thumbnail can miss the cache and pay a real render.

## Swimlane

`engineering/decisions/2026-08-10-thumbnail-window-is-two-way.md` § 4 (the recycle-cost analysis) and § 7 "Still open, deliberately" — surfaced by the adversarial trio on #1518.

## Done when

Either the two constants are reconciled (raise `SLICE_CACHE_MAX` to at least `PREVIEW_BUDGET`, or derive one from the other so they cannot drift apart), **or** a comment at each site states why the mismatch is correct. Plus a regression oracle: scroll Present's slide overview on a deck of 40+ slides down and back, and assert the engine render count for the return leg is bounded by cache hits rather than scaling with the traversal.

## How it arises

#1463's fix made the thumbnail window two-way, so a tile whose slot the budget reclaims is unmounted and re-rendered when the author scrolls back. The decision note prices that return as "cheap and cached" against the 24-entry slice LRU — true for a short deck, and false for exactly the long one the two-way window exists for. LRU eviction runs in the same direction as the scroll, so a down-and-back traversal of a 40-slide overview misses for everything more than 24 slides back.

## Scope note

This is the **slice** path (a plain deck). The whole-deck memo path — a deck carrying a deck-derived fact, where every overview tile renders the full deck and shares one parse — was a separate and more serious problem, and it *was* fixed in #1518 by refcounting live renderers in `dispose()`. This card is only about the slice cache's size relative to the budget.

Low priority: the cost is a re-render on a scroll-back, not a correctness or memory problem, and it is bounded. If #1538 makes the budget device-derived, revisit this together — the right relationship may be "cache ≥ budget" expressed once rather than two independently chosen numbers.
