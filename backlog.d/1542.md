# Read the divider flag off the engine's token stream — `blankCode` is the last hand-written approximation on the preview path

## Summary

Replace `blankCode`'s three regexes in `dividerDerivation` with a divider reading taken from the engine's own block tokens, so the preview cannot disagree with the engine about what code is.

## Swimlane

`engineering/decisions/2026-07-30-preview-deck-context-and-render-cost.md` — Amendment 7, § "The fix for that defect introduced a second one". The precedent is `engineering/decisions/2026-08-05-slide-boundary-reconciliation.md` (#1433), which retired the hand-written boundary scanner for the same reason.

## Done when

A deck built from each of the five shapes below supplies a divider section matching the engine's own rendered `<section class="… divider">` set — asserted in `test/unit/diagnostics/slice-equivalence-core.test.js` against `lib/engine` output as the oracle, not against the derivation's own reasoning. Plus: `npm run equiv` does not regress from 1325/1349, and `npm test` + `npm run build:check` stay green.

### The defect

`dividerDerivation` (`lib/diagnostics/slice-equivalence-core.mjs`) decides "is this chunk a divider?" by blanking code with three regexes and then matching a `_class:` directive. Those regexes are an approximation of markdown-it's block rules, and they disagree with it in **both directions**.

The per-chunk differential bail added in #1521 catches only the **over**-blanking direction (`blankCode` removes a directive the engine honors). It is structurally blind to **under**-blanking — `blankCode` failing to recognize code that the engine does — because then both readings agree and nothing disagrees. Confirmed against real renders, each supplying a divider the engine never renders:

| shape | why `blankCode` misses it |
|---|---|
| fence inside a blockquote — `> ```md` | the fence rule is anchored `^[ \t]*`, so a `>` prefix hides it |
| **unclosed fence** | i.e. any author part-way through typing a code sample |
| ` ``` ` opened, `~~~` closed | mismatched markers |
| double-backtick span — ` ``                        `` ` | the inline rule is single-backtick |

The unclosed-fence case is the one that matters: it is not an exotic deck, it is a normal deck **mid-keystroke**, and the preview grows a rail dot and then snaps back as the closing fence lands.

**All of these are pre-existing** — `main` returns the same wrong section — which is why #1521 logged them rather than folding them in. Zero committed decks trip them.

### Why the token stream

Same argument that settled #1433: an approximation of the parser can always be shown a shape it gets wrong, and each fix is an enumeration. Reading `fence` / `code_block` / `html_block` from the block tokens the boundary parse **already produces** cannot disagree, and closes all five shapes at once instead of one at a time.

The parse is already paid — `slideBoundaries` runs it and memoizes it — so this should be cost-neutral or better, but that needs measuring rather than assuming.
