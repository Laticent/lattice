# studio: `splitSlides` is blind to HEADING splits, so the caller's slide count disagrees with the engine's

## Summary

The Studio's `splitSlides` (via `separatorRanges` in `lib/core/slide-boundaries.mjs`) models **`hr` separators only**. The engine's default split is `split: headings`. So on any deck where a chunk contains more than one heading, the caller counts fewer slides than the engine renders — and every consumer of that count is wrong.

## This issue was originally filed against the wrong cause

It first said the two splitters "disagree about the empty leading chunk". The maker-checker on PR #1568 showed that is not it. Flip the #1551 repro deck to `split: rule` and the counts **agree and the bug disappears entirely** — the empty leading chunk is not the mechanism.

What actually happens: the pasted block's closing `---` is a **setext underline**, and the `<h2>` it produces is a *second heading in the chunk*, which the default heading-split ruler turns into a new section. Retitled and rewritten accordingly.

## Why it matters beyond #1551

This is not an edge case, it is the **default authoring style**. A deck with no `---` at all:

```markdown
# Title

## One

## Two
```

is **1 slide to the Studio and 3 to the engine** — verified against the real engine and the real splitter. That is the shape `examples/split-headings.md` markets ("write the outline, skip the separators"). Every count-consumer is off on such a deck: the slide rail, page numbers, `supplyablePosition`, the alignment guard (which fires and pushes every render onto the fallback), and the slice-equivalence sweep.

It also cost real safety margin in #1568: a guard written on the assumption that a 1→N chunk means an authoring error refused these decks outright, and had to be reworked to narrow instead. The blindness makes correct-looking guards wrong.

## What this needs

- Teach `separatorRanges` / `splitSlides` the heading split, via `headingSplitPoints` (`lib/core/heading-split-core.js`) — which `lib/core/bake-splits.js:53` and `lib/core/section-source-split.js:21` **already use**. So the capability exists and one caller is simply not wired to it (HARD RULE #1: one owner, all callers).
- Respect the deck's `split:` directive: `rule` must keep the current `hr`-only behavior, `headings` (the default) must add heading boundaries.
- Extend the real-engine alignment tier (`docs/src/lib/single-slide-render.alignment.test.ts`) with the outline-style deck — it already drives the real splitter and the real engine, which is what makes this class expressible.

## Blast radius — worth costing before starting

Fixing this **changes the slide count** on any deck relying on the default split, which moves the rail, page numbers and every supplied position. That is the correct answer, but it is a visible change to decks that render fine today, so it wants a corpus pass rather than a quick patch.

Note it does not remove the need for #1568's frame guard: the fallback stays reachable by other 1→N expansions (`glossary: auto` appends a slide; `_focusSteps` expands), so the frame still has to hold exactly one section by construction.
