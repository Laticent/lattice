# fix(studio): the crash report is invisible on the browser's own post-crash reload — three designs withdrawn

## Summary

Reported from a real phone (Firefox for iOS 18.7): *"when the page refreshes itself the crash report is not visible. i had to hit refresh to see the message."*

Immediate reporting requires `isSameTab()`, which requires the Navigation Timing type to be `reload`. On that browser the **browser's own recovery load is not typed `reload`**, so the record falls through to the 10-minute staleness wait and the one boot the user is actually watching says nothing. Pressing reload by hand produces a `reload` navigation, which is why the manual refresh appeared to work.

**Three designs were built for this and all three were withdrawn.** They are recorded here so the next attempt does not re-walk them.

1. **Watch the record for 21s; no heartbeat means dead.** Wrong against a comment twenty lines above it in the same file: a throttled tab writes a heartbeat about once every **five minutes**, which is why `STALE_MS` is ten minutes and not the 90s already found to harvest live background tabs. It would have announced that a duplicated tab's still-running original had crashed, offering a Discard button that deletes that live session's record. Reproduced against a session that had beaten 0 ms ago.
2. **Challenge/response over `localStorage`; no reply in 2s means dead.** Wrong against `STALL_MS` (2.5s) — the module's own threshold for "the main thread was blocked long enough to write down". Reproduced in two real Chromium tabs: block the live owner's main thread for 2.5s and the duplicate announces it crashed. Same mistake as (1), different clock.
3. **Hold a Web Lock for the life of the document.** The *right* primitive: the browser releases it on renderer crash, OOM kill and tab discard, and a frozen, throttled or blocked tab holds it as well as an idle one — no deadline to pick at all. Verified 6/6 in two real tabs. **Withdrawn anyway:** a held lock makes the page ineligible for the back/forward cache (Chromium 131, `notRestoredReasons: [{reason: "lock"}]`), and the release intended to prevent that can never fire, because eligibility is decided *before* `pagehide` so `persisted` is already `false` — the exact flag the release is gated on. That silently turns `live.bfcached = !!ev?.persisted` into dead code and with it the **entire iOS tab-eviction path**, on the platform the report came from.

## Done when

On a **real device** (state which), against the deployed site, with a Studio tab that dies without a manual reload:

1. The report surfaces on the browser's **own** reload — no manual refresh — within seconds, not ten minutes.
2. With two Studio tabs open, background one until the browser throttles it (>5 min), then duplicate it. **Assert: the duplicate never reports the live original as crashed.** This is the property all three withdrawn designs broke; it is the acceptance criterion, not a nice-to-have.
3. Block a live tab's main thread for 5s while another tab boots. **Assert: still no report.**
4. `pagehide`'s `persisted` still reaches `live.bfcached` — i.e. whatever the fix does, the iOS eviction signal still works. Verify by observing a `bfcached` record, not by reading the code.

State which browser and how each was produced. A unit test cannot close this card: jsdom has no `navigator.locks` and does not deliver `storage` events between documents, which is how designs (1) and (2) both passed their suites.
