# e2e: playground-first-paint's cut-document width read takes an unguarded boundingBox() and can hit null on CI

## Summary

`docs/e2e/playground-first-paint.spec.ts:261` — the `@smoke` case *"the editor pane holds its
width before the preview pane has parsed"* — reads a bounding box and dereferences it with `!`:

```ts
const width = (await page.locator('#pg-split-editor').boundingBox())!.width;
```

`boundingBox()` **resolves with `null`** for an element that currently has no box; it does not
wait for one. On CI that produced:

```
TypeError: Cannot read properties of null (reading 'width')
  at docs/e2e/playground-first-paint.spec.ts:261:72
```

The `settled` read at `:240` has the same unguarded shape.

### Where it was seen

`studio-smoke` on PR #1849, run
[32845276580](https://github.com/SlideWright/lattice/actions/runs/32845276580/job/97793525601)
(1 failed, 17 passed). The same job was **green on the previous head of the same PR**, and the
spec is untouched by that diff — its last change is `5e05180` (#1817).

### Not caused by the PR that found it

PR #1849 changes `ArchitectChat.tsx`, `studio-fixture.ts`'s `controlReady`, and three e2e specs.
`playground-first-paint.spec.ts` is not among them, imports nothing that changed (`expect`/`test`
from the fixture, plus the `pg-split` constants), and does not call `controlReady`. So this is
pre-existing and off that change's path: HARD RULE #18's log-don't-widen branch, which is why it
is filed rather than folded in — the same treatment #1813 and #1815 got.

Worth noting for whoever picks it up: `studio-smoke` is **advisory by design**. `ci.yml`'s `ci`
gate needs `lint`/`unit`/`integration`/`docs-build` and deliberately not this job, pending the
nightly green streak in #800. So this is a signal-quality problem, not a merge blocker — which is
exactly the #1328 bill: a tier that cries wolf teaches people to dismiss it.

### Not reproduced locally — what was tried

Against the built site (`astro preview`), all green:

| attempt | result |
|---|---|
| the case alone, `--repeat-each=4 --workers=2` | 4/4 pass |
| the cut-document flow under `Emulation.setCPUThrottlingRate` 8×, 6 runs | immediate `boundingBox()` non-null every run |
| the full tier as CI runs it (`--project=desktop --grep @smoke --workers=2`), twice | 18/18, 18/18 |

So the window is CI-runner-specific (2 cores) — consistent with the spec's own header, which
records that the sampling case beside it "on a 4-core box … never is [wide enough], and on the
2-core CI runner it was". What is established is the failure mode: the locator resolved and the
box was absent at that instant, with nothing waiting for it.

### Suggested fix

Wait for a box instead of asserting on a first read — the same principle the spec is about,
applied to its own measurement:

```ts
const editor = page.locator('#pg-split-editor');
await expect(editor).toBeVisible();
const width = (await editor.boundingBox())!.width;
```

Apply it to both reads (`:240` and `:261`). This does not weaken the oracle: the assertion is
about the pane's *width*, not about how soon it has one, and the cut document removes the preview
panel permanently — so nothing can narrow the pane later and slip past a wait.

Worth confirming the reproduction on a 2-core runner first, since one CI observation is thin.
