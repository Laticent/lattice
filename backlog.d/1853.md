# feat(export): no way to export a lens — reader views cannot leave the Studio as files

## Summary

A deck can carry any number of reader lenses, and the projection logic is shipped and correct — but there is no way to *export* one. The CLI has no `--lens` flag and the Studio's share/export path has no lens awareness, so a lens exists only as a live view inside Studio. "One source, many audience views" currently means "one source, many audience views, none of which you can send anyone as a file."

## Swimlane

`engineering/decisions/2026-07-13-lente-reader-lenses.md` — the Lente design record. This is the missing consumer at the end of that design: the record covers authoring, suggesting, approving and reading, and stops short of exporting.

## Done when

`lattice deck.md --lens investor out.pdf` renders only the slides the `investor` lens projects, in author order, and refuses with a non-zero exit and a named reason when the lens is unavailable (`unknown` / `hidden` / `unapproved` / `empty` / `drifted`) rather than silently falling back to the full deck. A unit test asserts the fail-closed path for each of the five reasons, and an integration test asserts page count equals `lensSlides(...).length` for an approved lens.

### Evidence

**The CLI has 34 flags and none of them is `--lens`.**

```
$ grep -oE "'--[a-z-]+'" lattice-emulator.js | sort -u | tr '\n' ' '
--captions --css --embed-source --fluid --help --image-format --image-mode
--image-quality --image-size --keep-vector-images --no-split --no-svg
--no-thumbnails --notes --notes-icon --orientation --output --overflow-marker
--palette --paper --player --present --print --quiet --raster --strip-captions
--strip-notes --svg-background --thumb-width --version …

$ grep -c "lens" lattice-emulator.js
0
```

Zero occurrences. Note the flag set already covers the adjacent concerns — `--palette` swaps the theme, `--paper` picks the sheet, `--notes` / `--strip-notes` include or drop a content channel, `--present` and `--player` change the output mode. A lens is the same shape of thing and is the only one missing.

**Studio's export path is equally unaware.** `docs/src/components/studio/share-export.ts` contains no reference to lenses. Eight Studio modules mention `lens` (`architect.ts`, `lens-archetypes.ts`, `lint.ts`, `slide-directives.ts`, `preview-rect.ts`, `studio-language.ts`, and two tests) — the export module is not among them. So neither exit from the product can project a lens.

**What the reader gets instead.** `_lens` is a flag directive (`lib/engine/directives.js:76`, `FLAG_DIRECTIVES`), so tags are stripped from exported bytes and every export is the full deck. That stripping is correct and should not change — the defect is that nothing *filters* before it.

### The work is smaller than it looks

Everything needed already ships and is already Node-importable:

| Piece | Where | Status |
|---|---|---|
| Parse the `lenses:` block | `parseLensRegistry` | shipped |
| Compute membership | `lensSlides` / `lensPairs` | shipped |
| Fail-closed eligibility with 5 named reasons | `lensEligibility` (`docs/src/lib/lente/project.ts:71-81`) | shipped |
| Built CJS + ESM distribution | `docs/src/lib/lente/dist/` | shipped |

**`checkLenteBoundary` does not block this.** The gate iterates files *inside* `LENTE_DIR` and rejects imports that escape the folder, allowing `./` relatives and `node:` built-ins. It constrains what Lente may reach out to; it says nothing about what may reach in. That one-directional purity is exactly what makes the library safe for the engine to consume.

Demonstrated: `require('./docs/src/lib/lente/dist/index.cjs')` works from plain Node in this repo today — it was used repeatedly during the executive-briefing review to compute projections and eligibility outside any browser.

The genuine open question is **placement**, not permission: Lente currently lives under `docs/src/lib/`, and an engine-side CLI consuming a docs-side library is a layering choice worth a deliberate decision (move it, publish it, or accept the direction). That belongs in triage.

### Why this matters more than a convenience flag

The lens system's entire value proposition is one source file serving several audiences. Today that value is only realized for a reader who (a) is online, (b) opens your Studio, and (c) is looking at a deck whose lenses you have approved. Anyone who needs a file — an emailed board pack, an attachment to a procurement thread, a printed leave-behind — gets the full deck or nothing.

The current workaround is page surgery. To produce a three-page projection of `examples/lattice-executive-briefing.md`, the pages were rendered as the full 52-page deck and then extracted:

```
pdfseparate -f 2 -l 2 … && pdfseparate -f 8 -l 8 … && pdfseparate -f 48 -l 48 …
# then merged with pdf-lib
```

That requires knowing the absolute page numbers of a lens's members, which is exactly the coupling lenses exist to remove, and it silently breaks the moment a slide is inserted.

### Slices

- [ ] **1 — Decide placement.** Engine imports `docs/src/lib/lente`, Lente moves to `lib/`, or the projection is reimplemented engine-side. This gates everything else and is a layering decision, not an implementation one.
- [ ] **2 — `--lens <id>` on the CLI.** Filter slides through `lensSlides` after front-matter parse and before render. Must route through `lensEligibility` and exit non-zero with the named reason when ineligible — never fall through to the full deck, which would defeat the property the lens system is built on.
- [ ] **3 — Tests.** Unit: each of the five unavailable reasons refuses. Integration: an approved lens renders exactly `lensSlides(...).length` pages, and `--lens full` equals the default output.
- [ ] **4 — Studio share/export.** Offer the active lens as an export target in `share-export.ts`, so the two exits behave the same.
- [ ] **5 — Docs.** `design/skills/lens.md` and `engineering/pipeline.md` currently describe lenses as a reader-side feature; both need the export path once it exists.
