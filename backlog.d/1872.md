# test(split): the split oracle's `verified` map is empty — 28 enrolled components pinned against drift, none attested as correct

## Summary

`test/oracle/split-oracle.json` carries **61 components**, 28 of them enrolled with a split recipe, and its `verified` map has **zero entries** (parsed, not grepped).

All 28 sit in the `GRANDFATHERED` list, which the file's own `$comment` calls *"a shrink-only backlog, not an exemption."* The backlog has not shrunk.

## What this does and does not guarantee

The gate (`checkSplitOracle`, `tools/check-ownership.js:7827`) is real and does useful work — it fails on drift, and it enforces the attestation precondition for **newly** enrolled components. So a split behavior that changes without review is caught.

What is not established is whether the pinned behavior was **right in the first place**. For all 28 existing entries the oracle pins a derived fact with no record of a committed deck that exercises it or a human who signed it off. It protects the answer without ever having checked the answer.

## Why it belongs with #1859

This is the same defect shape as the Marp fidelity ledger: **the contract is written down, and the gate reads the writing rather than the behavior.** In one case an empty `verified: {}` means a declaration nobody attested; in the other, `coverage: 'mirrored'` is backed by a substring match on a function name. Two isolated nits individually; one credible systemic observation together — and the second one already let a real defect ship (#1858).

Worth deciding as one idea: what does an attestation have to *be* in this repo before a gate is allowed to treat a declaration as true?
