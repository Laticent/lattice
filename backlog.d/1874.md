# feat(orchestration): add the ADDITIVE TRIO — seam census, blast radius, contradiction resolution — as roster agents alongside the adversarial trio

## Summary

Add three generative lenses to `.claude/agents/`, using the same mechanism as the adversarial trio, and name the pair explicitly:

| | **Adversarial trio** (exists) | **Additive trio** (this issue) |
|---|---|---|
| direction | **subtractive** | **additive** |
| asks | is this claim true? where does it break? | what is here that nobody has named? |
| lenses | `red-team` · `inversion` · `checker` | `seam-census` · `blast-radius` · `contradictions` |
| input | a claim, a design, a diff | a system, a corpus, a question |
| output | attacks, refutations, verdicts | joins, dependencies, refused tradeoffs |

**Naming rule (required, and the reason this issue exists as much as the agents do):** *"the trio"* on its own means **the adversarial trio** — the existing default, unchanged. The additive trio must be named in full. When a request is genuinely ambiguous, **ask** rather than guess; the two do opposite work and running the wrong one produces confident, well-formed, useless output.

## Why a second trio

The adversarial trio audits claims you already have. It **cannot generate** them. Run it on a body of work whose *framing* is wrong and it returns a better-defended version of the wrong argument — which is exactly what happened during the executive-briefing work: a full trio pass hardened a deck that was built on the wrong thesis, and only a different instrument found the right one.

The two are complementary, not ranked. One finds what is there; the other checks whether it is true.

## The three lenses

**1. `seam-census` — enumerate the JOINS, not the parts.**
For each A→B in the system, ask what the join produces that neither side does alone. Kill anything that turns out to be one feature with two names. Rate each seam as emergent or not, and name the closest competitor to each.

**2. `blast-radius` — delete one thing; what dies?**
Walk real `require`/`import`/dynamic-import edges and compute reverse-dependency closures. Rank by how many user-visible capabilities die on removal. A component whose removal kills nine things is load-bearing regardless of how it scores on any per-item rubric — which is precisely what per-item scoring cannot see.

**3. `contradictions` — which forced tradeoffs does the system refuse?**
Enumerate the tradeoffs the field treats as unavoidable. For each: does this system refuse it, by what mechanism, at what cost, and who else has tried? **Then enumerate the ones it does NOT resolve** — that second list is the more valuable half.

## Pilot evidence

All three were run ad hoc this session against the Lattice composition question. Returns:

- **`seam-census`** → 24 seams; five written in executive form.
- **`blast-radius`** → the three-layer stack (markdown → `_class` grammar → 61 manifests), ranked by what dies: manifests ~10 capabilities, the grammar ~9, `slide-boundaries.mjs` ~7 across 87 non-test modules. Plus 7 load-bearing capabilities no doc names.
- **`contradictions`** → 9 refused tradeoffs with mechanisms and prices, and 10 not resolved.

**The most valuable output was the kill lists, not the findings.** Each lens independently refused to assert something it was asked to find, and three of those refusals became tickets: lens-in-player was false as written (**#1854**); the exported player is one input verb short (**#1578**); and one lens inherited retired forgery/redaction wording straight from a stale skill file (**#1867** — direct evidence that stale prompts propagate into fresh agent output months after the correction was recorded).

It also flagged the single most falsifiable claim in the marquee — a competitor comparison row with **no harness in-tree producing it** — and conceded a genuine architectural trade rather than claiming a win.

## Two observed failure modes the cards must address

1. **A partial truth reported as a kill.** `seam-census` correctly found that capacity "never triggers a split" and concluded it was advisory. The adversarial `checker` later showed `lint:deck:all --strict` is both a CI step and a pre-push hook, so capacity **does** fail the build. Both halves were true; reporting one as the whole was the error. → Each card must require distinguishing **"not traced"** from **"false"**, and must state what would settle the difference.
2. **Inheriting a retired claim from a prompt file.** → Each card must require verifying load-bearing claims against **source**, never against `design/skills/**` or other prose, and must call out any claim it took from a doc rather than from code.

## Implementation

**Roster cards** — `.claude/agents/{seam-census,blast-radius,contradictions}.md`, matching the shape of `.claude/agents/red-team.md`:
- frontmatter `name` / `description` / `tools: Read, Grep, Glob, Bash` / **`model: opus`** (HARD RULE #27, gated by `checkAgentModelPinning` at `tools/check-ownership.js:7408`)
- each body opens by naming its two siblings and saying **"do not do their jobs"**, as `red-team.md` does
- each carries a governing assumption, a where-to-look section, and an explicit **kill-list requirement** — a pass that finds no unsubstantiated claim has probably not looked

**`engineering/orchestration.md`** — a new top-level section. **Not a rung on the verification ladder.** That ladder (tier 0 / 1 / 2) scales *verification* effort with blast radius; the additive trio is a different axis entirely — discovery, not verification. Filing it under the ladder would invite people to run it where the adversarial trio is mandatory, which is the one confusion this issue must prevent. It also needs the disambiguation rule stated where agents will read it.

**`CLAUDE.md`** — three rows in the roster table (§MODEL POLICY), and the disambiguation rule in §MAKER-CHECKER or beside the HARD RULE #25 reference, so it reaches an agent that never opens `orchestration.md`.

**Optional — `.claude/workflows/additive-trio.js`.** Precedent: `design-competition.js`, which carries a committed hard agent cap at line 26 that HARD RULE #25's >10-agent exemption reads off. Worth doing if the three are usually run together (they were in the pilot, in one parallel phase feeding a synthesis the human owns). Ad-hoc `Agent()` calls work fine without it and ride on the model policy.
