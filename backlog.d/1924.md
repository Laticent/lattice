# infra(build): rebuilding a gallery PDF invalidates the showcase WebP, and nothing chains or checks it locally

## Summary

`docs/public/showcase/*.webp` is derived from the component gallery PDFs. Rebuilding a gallery invalidates them, but `npm run build` doesn't chain the rasterizer and no local gate notices — so the miss is only ever caught on CI, one full push-and-wait cycle at a time.

## Swimlane

None — a build-ordering papercut. Adjacent to `engineering/workflow.md` §Merging (the pre-push checklist is where the answer probably belongs).

## Done when

Rebuilding a chart gallery and committing without re-rasterizing either fails locally before the push, or cannot happen because the build chains the two. Done when the sequence `build-galleries --only X` → commit → push cannot produce a red `showcase:check` on CI.

---

## Observed

On #1631, twice, for the same reason:

1. Rebuilt the 14 chart-bucket galleries → pushed → `docs-build` red on `showcase:check` (funnel, radar, roadmap stale).
2. Fixed a clip, rebuilt the affected galleries again → pushed → **same check red again** (roadmap).

Each miss cost a full CI cycle. The fix both times was one command:

```
node docs/scripts/rasterize-showcase.mjs
```

## Mechanism

`docs/scripts/rasterize-showcase.mjs --check` compares each committed WebP against the gallery PDF it was rendered from, and fails when the PDF is newer:

```
stale: funnel.light: gallery PDF changed since the WebP was generated (drifted render)
```

The check is correct and its message names the fix. The gap is *when* it runs: `showcase:check` is the first step of `docs/`'s `build`, which runs on CI. `npm run build` and `npm run build:check` at the repo root do not reach it, and neither does any hook.

So the ordering — **rebuild galleries → re-rasterize showcase → commit** — is held only by whoever remembers it.

## Candidate shapes

- **Chain it.** Have `tools/build-galleries.js` invoke the rasterizer for any component in the showcase set. Most direct; couples the engine build to `docs/`, which may be unwanted.
- **Gate it locally.** Add `showcase:check` to the pre-push hook, or to root `build:check`. Cheap (it is an mtime comparison, no rendering) but needs `docs/` deps present — see #1537, which is exactly the failure mode where they aren't.
- **Document it.** Add the ordering to `workflow.md`'s pre-push checklist. Weakest, but free.

Only ~10 of the components are showcased, so the coupling is narrower than it first looks — a targeted chain is plausible.
