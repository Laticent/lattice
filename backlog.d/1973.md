# Expose categorical tokens as Mermaid-consumable node classes, so `:::` can pin an entity's color

## Summary

Ship palette-token-backed CSS classes that a deck author can attach with Mermaid's `:::className` shorthand, so a recurring entity keeps one color across every diagram in a deck.

## Swimlane

`engineering/mermaid.md` § "the theming contract" + the band cycle in `lib/integrations/mermaid/mermaid.css:689-698`. No decision doc governs author-side color control yet; this card is the first ask for it.

## Problem

Flowchart node color is a pure function of **DOM position**:

```css
/* lib/integrations/mermaid/mermaid.css:689 */
:is(section, figure) g.nodes > g.node:nth-of-type(1) > rect { fill: var(--cat-1-fill) !important; … }
```

The rule is generic (`g.nodes > g.node`), not sankey-specific as the comment above it suggests, so it governs flowcharts too. An author therefore cannot say "this node is the platform, paint it consistently" — the same entity changes color between slides purely because it was declared in a different order.

Measured on a real 22-diagram deck: one entity rendered `--cat-3` on one slide, `--cat-5` on another and `--cat-8` on a third, with no authoring difference other than declaration order. For an architecture deck whose subject *is* which box owns what, that actively fights the message.

### Neither existing lever solves it

- **`classDef … fill:var(--cat-3-fill)` is a parse error.** Mermaid's classDef grammar rejects `var()`:
  `⚠ Mermaid render failed for one diagram: Parse error on line 3`
- **`classDef … fill:#hex` works but is off-palette** — Mermaid emits it as an inline `style="fill:#… !important"`, which does beat the stylesheet cycle, but a baked hex cannot flip with `color-scheme` and violates the spirit of HARD RULE #3.

The only workaround today is to hand-order node declarations across every diagram in the deck, which is fragile, invisible to the next author, and constrains layout.

## What already works (measured)

Mermaid's `:::` shorthand **already reaches the SVG** — Lattice just ships nothing to attach:

```
flowchart LR
    A[Caller] --> DP[Data Plane]:::platform
```
```html
<g class="node default platform">
```

And a token-backed class rule appended after the band cycle **wins over it**, verified against the real bundled `dist/lattice.css`:

```css
:is(section, figure) g.nodes > g.node.cat-3 > rect {
  fill: var(--cat-3-texture, var(--cat-3-fill)) !important;
  stroke: var(--diagram-stroke) !important;
}
```

With `DP[Data Plane]:::cat-3`, the node held `--cat-3` whether declared **first** or **last** in the source, while unclassed nodes kept cycling. Same specificity as the `:nth-of-type()` rule, so source order decides — the class block must come after the cycle.

## Design note: pinning creates collisions

In the same test, pinning one node to `cat-3` left an unclassed node at positional band 3 — **two nodes rendered the same fill**. Whatever shape this takes should say what happens to the residual cycle. Options worth weighing:

1. Cycle skips bands claimed by a class in the same diagram (best read, most work).
2. Pinning is all-or-nothing per diagram — any `:::` disables the positional cycle.
3. Document the collision and leave it to the author (cheapest, worst footgun).

Also worth deciding: raw `cat-N` names, or semantic aliases, and whether the paired ink (`--cat-on-fill`) and `--cat-N-texture` a11y channel come along automatically.

## Done when

- A deck can write `DP[Data Plane]:::cat-3` and the node renders `--cat-3-fill` regardless of its declaration position, in **both** light and dark, with no hex in the deck source.
- The class names are documented in `engineering/mermaid.md` with the collision rule above stated explicitly.
- A unit or integration test pins the behavior: same node, two declaration positions, one resulting fill.
- The `--cat-N-texture` a11y channel and paired ink still resolve on a classed node.
