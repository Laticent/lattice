# fix(list): an inline-code chip in a list card swallows the space beside it

## Summary

In a `list` card, an inline-code chip renders flush against the neighboring word — the space
next to it is in the markup and does not reach the page. The same chip in a `content`
paragraph spaces correctly, so this is scoped to the card, not to inline code generally.

Found while authoring `examples/lens-export.md` for #1853/#1854. **Not caused by that
change** — logged rather than pulled into the diff (HARD RULE #18, off-path pre-existing).

## Evidence

Source, in a `                     ` slide:

```markdown
- A `lenses:` block in front matter names each view and its approval hash.
```

The rendered HTML sidecar keeps the space — so the markup is right:

```html
<li>A <code>lenses:</code> block in front matter names each view and its approval hash.</li>
```

The PDF renders it as `A [lenses:]block` — no gap between the chip's right border and `block`.
Confirmed at 300 DPI, and **both rasterizers agree**, which is the check
`engineering/gotchas/css.md` asks for before believing a `pdftoppm` reading:

```
pdftoppm  -r 300 -f 3 -l 3 …   # flush
pdftocairo -r 300 -f 3 -l 3 …  # flush
```

Rewording so the chip lands at the end of the card moved the loss to the **other** side —
`called[lenses:]` — so it is the space adjacent to the chip that is lost, whichever side it
is on, rather than a trailing-space-only bug.

## Why it looks like the card, not inline code

`examples/debug.pdf` — committed, untouched, last built 2026-08-30 — puts two chips
mid-sentence in a `content` slide and both space correctly on both sides:

> …the boxes are just noise. `off` is also the default everywhere: with no `debug:` key at
> all, the preview is clean.

Same engine, same `section code` rule (`lib/base/base.elements.css:130`, symmetric
`padding:0.15625cqi 0.46875cqi`). The difference is the component around it.

## Suggested starting point

The chip rule itself is symmetric, so look at the list card's own text layout — a
`white-space`, `display`, or flex/gap treatment of the card's inline content that drops the
space adjacent to an inline-level box. Worth checking whether other card-style components
(`cards-grid`, `list-steps`) share it, since they share the card shape.

## Workaround until fixed

Keep inline code out of `list` card bodies, or place it where no space is needed beside it.
`examples/lens-export.md` does the former.
