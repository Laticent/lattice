# split: a component cannot declare a density limit without also opting into being split

## Summary

`capacity` and `split` are one switch. `splitFactsFor` computes `enrolled: Boolean(axis || split)` (`lib/core/split-facts.js:354`), so declaring a density limit is the same act as consenting to pagination. For a component that must never be split, there is no way to say "past N items this is too dense" at all.

Found while trying to close the manifest gap #1605 names.

## Concretely

#1605 asks for `quadrant` to declare its density limit:

> `quadrant.manifest.json` declares neither `capacity` nor `split`. Roadmap has both … Quadrant's density limit exists only as prose in `antiPatterns` — *"Past twelve the labels overlap and the quadrant becomes a constellation"* — so the recommender can't warn, lint can't flag, and the engine can't paginate.

I wrote the block. The oracle gate rejected it, correctly:

```
quadrant: §0c places it as 'graphic' (never splits — overflow rings), but the
manifest opts INTO splitting (axis=items in capacity, strategy=null). The split
registry reads either as an opt-in, so this ships a split that destroys the
component's meaning — the #1193 defect class (matrix-2x2 was shredded into
2-of-4 quadrants this way).
```

`enrolled` went `false → true` on nothing but the presence of a `capacity.axis`. And a quadrant split across pages is not a quadrant — you get two of four cells, which is the exact defect #1193 is about.

So #1605's ask is currently unbuildable: the warning it wants and the split it must not have are the same declaration.

## Why the conflation is not obviously wrong

It is load-bearing for everything that *does* split. A component that declares "8 per page" is saying what a page holds, which only means something if there are pages. The rule catches a real class of mistake — `matrix-2x2` was shredded exactly this way — and `treatmentViolations` fails on a stale or contradictory pairing, which is why the gate caught this attempt rather than shipping it.

The gap is that `NEVER_SPLIT` components have a density limit too. It just resolves to *ring the overflow marker and coach the author*, not *paginate*.

## Suggested shape

A capacity declaration that carries its own remedy, so `enrolled` stops being inferred from the field's mere presence. Roughly:

```jsonc
"capacity": {
  "axis": "items",
  "soft": 12,
  "onExceed": "warn"    // vs the implied "split" everything has today
}
```

`splitFactsFor` would then compute `enrolled` from `onExceed === 'split'` (or from `split` being present), and `treatmentViolations` would gain the inverse arm: a `NEVER_SPLIT` component declaring `onExceed: "split"` is the #1193 mistake, and one declaring `onExceed: "warn"` is fine. Every existing `capacity` block keeps today's meaning by defaulting `onExceed` to `split`, so this is additive.

That unlocks three things #1605 lists, without touching pagination: the recommender can warn, `lint:deck` can coach (HARD RULE #29's posture), and the density limit stops being prose in `antiPatterns` that nothing reads.

## Not in scope

Whether `quadrant`'s limit is 12 (the `antiPatterns` prose) or something else. #1605's own measurement says item count is not the whole story — label length and dot proximity bind too — so the number is a separate question from the mechanism.
