# The plugin packages: `@laticent/plugin-api`, a private `package.json` per plugin, a top-level `packages/`

## Summary

the Hollywood note's step 5. Today a plugin's allowed imports are the gate's rule (own folder, the workspace libraries, the plugins it `requires`); a private package.json makes them the plugin's own declaration, which is what an npm plugin will carry, and `@laticent/plugin-api` gives the contract (ctx types, manifest schema, `api` versions) one home instead of spec/LPM.md plus resolve.js.

## Swimlane

engineering/decisions/2026-11-01-plugin-contract-hollywood.md §5, §9

## Done when

every workspace library `lib/` imports lives under packages/; `@laticent/plugin-api` exists and resolve.js reads `KNOWN_API` from it; each in-tree plugin has a private package.json mirroring the engine's version, and the structure gate holds each plugin to its declared dependencies; `npm pack` shows the root tarball unchanged in what it ships. Publishing them stays an owner decision (§7 Q3). Note for that decision: `@laticent/markup` is marked `"private": true` (docs/src/lib/markup/package.json) yet the engine requires it at runtime, so a `npm publish --workspaces` would skip it and leave the published engine unresolvable; the other eight workspace libraries are unpublished but not private (red team on #2997). Also: tools/library-prepack.js (every library's `prepack`) refuses to run outside docs/src/lib/, so the move must update its folder check, or every library publishes with no dist/ built.
