# Measure and simplify what the Studio costs a phone to boot

## Summary

Measure what the Studio costs a phone from page open to first edit, map which of its boot mechanisms do the same job twice, and write a design note that keeps, merges or deletes each one before any code changes.

## Swimlane

None yet. Step 4 below writes it (`engineering/decisions/YYYY-MM-DD-studio-boot-simplification.md`).

### Why

Two days chasing iOS Simulator failures (#3519, #3523, #2988) found the macOS runners overloaded, and the bigger runner trial fixed most of it (5 of 6 green, 0 swap-outs against about 124,000). That hides the symptom in CI. A real phone has less room than either runner and loads the same Studio. What the hunt measured along the way:

| Finding | Number |
|---|---|
| One component holds most of the Studio | `docs/src/components/studio/StudioShell.tsx` is 9,758 lines; the folder holds 583 files |
| The Studio page loads in many small pieces | 187 `/_astro/` files fetched on a first load (run 45453722865) |
| The JavaScript it loads up front | cap 644,780 B gzipped (`docs/route-budget.json`, `studio.eagerJsGz`), raised twice in two days (#3512, #3516) |
| Diagnostic tools ship to every visitor | `studio.astro` mounts `VizDiagnosticsOverlay`, `PreviewFidelityOverlay`, `ViewportDebugOverlay`, plus `SiteDiagnostics`, `PerfOverlay` and the crash sentinel, at boot |
| One failed piece leaves the Studio blank | Safari keeps a failed module in its module map, so astro's one import retry cannot recover the island (iPad, run 45460220846; `followups.d/3368-p1`) |
| Safari's page process in the simulator | about 1 GB (runs 45548302899, 45552549848) |
| The first paint is guarded by stacked mechanisms | the newcomer bake, the shimmer placeholder, the measured split in a frame, its structural fallback, timeouts on that fallback (`within-ms.ts`), the engine prefetch, the page-lifetime theme fetch, and the service worker's `cacheFirst` over all of it. Each was added to stop a jump or a wait the one before it left. |
| Browser storage, spread wide | `localStorage` in 91 files under `docs/src` with about 200 distinct `lattice-*` keys, `sessionStorage` in 17, IndexedDB in 11 (3 databases: `lattice-secrets`, `lattice-studio-chats`, `lattice-studio-versions`), Cache Storage in 8. `localStorage` and `sessionStorage` are synchronous: every read blocks the page until it returns, and each module reads its own keys when it first needs them, so no one place owns stored state |
| The rules around it | `tools/check-ownership.js` is 16,417 lines with 842 `SANCTIONED_` entries; 297 decision notes; CLAUDE.md is 792 lines |

Some of this is the product: the sanitizers, measuring real text to fit a slide, offline use, slides that do not jump. The question is how many separate mechanisms each one is now spread across, and which a simpler design would not need.

### Where stored data lives, and the right home for each kind

What the Studio keeps in the browser today (found 2026-11-25, `docs/src`):

| Store | What is in it |
|---|---|
| IndexedDB `lattice-workbench` (`components/studio/library/asset-store.js`, `media-store.ts`) | **A person's photos and videos** as Blobs, plus themes, components and their version history. Named for the Workbench, a product that was removed |
| IndexedDB, poster store (`components/map-rail/poster-store.ts`) | Pictures again, as raw bytes, **because its header says Blobs in IndexedDB have failed in WebKit**, while the photo store above relies on Blobs |
| IndexedDB `lattice-studio-chats`, `lattice-studio-versions`, `lattice-narration`, `lattice-secrets`, `lattice-live`, `lattice-filo` | Chats, checkpoints, narration, encryption keys, live sessions and more: six more databases, each with its own version and migrations |
| IndexedDB `lattice-drawing-board` | Kept only to migrate data out of the retired Drawing Board |
| `localStorage` / `sessionStorage` | About 200 `lattice-*` keys across 91 and 17 files, read one at a time, each read blocking the page |
| Cache Storage | The service worker's app files, plus downloaded on-device model files (`architect-model.js`, `voice-model.js`) |

**Problems, most serious first:**

1. **Nothing asks the browser to keep a person's work.** There is no `navigator.storage.persist()` call anywhere in `docs/src`. Without it, Safari treats the site's storage as disposable: it can delete it under storage pressure, or after about seven days without a visit, **including stored decks and photos**. This is a data-loss risk, not tidiness, and it is the first thing to settle.
2. **Two stores disagree about Blobs in Safari.** One avoids them as unsafe in WebKit; the photo store depends on them. One of the two is wrong, and the probe that finds out runs on the real iOS Simulator, not a harness.
3. **About nine databases**, each versioned and migrated on its own, some named for products that no longer exist.
4. **About 200 settings keys**, each read synchronously by the module that wants it.

**The usual right home for each kind** (the design note in step 4 checks each against what the Studio needs):

- **A person's own files** (photos, videos, decks, history): records in one IndexedDB database with one owner module, versioned once; large media (photos, videos) in the Origin Private File System if the measurements say it reads faster and lighter (see below).
- **Small settings:** one record, read once at boot, written through one module.
- **Downloaded app files and models:** Cache Storage, owned by the service worker.
- **Durability:** ask for persistent storage at the moment a person first saves something of their own, and show them when the browser refused.

**The browser's file stores, and what each can and cannot do:**

- **The Origin Private File System (OPFS)** (`navigator.storage.getDirectory()`): a private folder per site, in Chrome, Edge, Firefox and Safari, including iPhone Safari. Built for big binary files: a file can be read or written in parts without loading it whole, which suits photos and videos better than whole Blobs in IndexedDB. Two limits: the person cannot see it (it is not their Files app or Finder), and **it follows the same eviction rules as IndexedDB**, so without `persist()` Safari can still delete it. Moving data there does not by itself make it safe.
- **The File System Access API** (`showOpenFilePicker`, `showDirectoryPicker`): opens and saves real files on the person's disk through a picker. Chrome and Edge only; **not Safari, not Firefox, not iPhone**. It cannot be the Studio's main store, only an extra such as "save this deck to a folder" where the browser offers it.

**One storage interface, two backends.** The Laticent desktop app (Tauri) will live in this repository and wrap the same Studio, and it has the real file system. The design note should give the Studio one storage interface with a browser backend (IndexedDB for records, OPFS for large media if the measurements favor it) and a desktop backend (real files), so the desktop app inherits the storage layer instead of forcing a second rewrite.

**Durability comes from three things together**, whatever the store: a `persist()` request when a person first saves something of their own, telling them when the browser refuses, and an easy export or backup so they always hold their own copy.

Any move between stores migrates every existing record and proves it on a copy of a real stored workspace before it ships. **No person's stored deck, photo, chat or setting may be lost or reset by a move.**

### What "cut" means here

A cut removes or merges a mechanism so the Studio does the same job with less machinery. The person using it sees the same thing, or better. **It never means dropping a feature someone relies on.** A cut takes one of four forms:

1. **Delete what nobody needs at that moment.** Example: the debugging panels (`VizDiagnosticsOverlay`, `PreviewFidelityOverlay`, `ViewportDebugOverlay`, `PerfOverlay`) load for every visitor today. A cut loads them only when a developer asks, for example with `?debug` in the URL. Visitors see no difference; the page downloads less, runs less code and has fewer files that can fail.
2. **Merge two mechanisms that do one job.** Example: four pieces cooperate so the first slide appears without jumping: the newcomer bake, the shimmer placeholder, the measured split in a frame, and its fallback when that is slow. If one well-designed step does that job, the other three go, along with the timeouts between them.
3. **Load in fewer, larger pieces.** Example: the Studio fetches 187 script files before you can edit. Grouping them into a handful means fewer downloads, and fewer chances for one failed file to leave the Studio blank (the iPad failure in run 45460220846).

4. **Read stored state once, from one place.** Example: today about 200 `localStorage` keys are read by 91 files, each when its module first loads, and every read blocks the page. A cut gathers what the first paint needs into one read at boot, moves the rest to when it is used, and drops keys nothing reads any more. Stored decks, settings and chats stay exactly as a person left them; a cut that would lose or reset stored data does not ship.

**Every cut carries its proof.** Its PR shows before and after numbers from step 1 below (bytes, files, time to first slide, time to first edit, memory) and shows that nothing a person sees got worse. A cut that cannot show that does not ship.

**Nothing is cut before the owner sees the design note** (step 4), which lists each mechanism as keep, merge or delete, with its reason and measured cost. The owner decides which cuts happen.

## Done when

1. **Measured cost, on a phone-sized profile** (Playwright WebKit with an iPhone viewport and CPU throttling, plus the iOS Simulator suite's own recorders): bytes, request count, main-thread busy time and memory, from page open to first slide shown and to first edit. Storage too: how many `localStorage` / `sessionStorage` reads and writes happen before first edit, the time they take, the bytes stored, and how many IndexedDB and Cache Storage opens and reads, with a stored deck and without one. Recorded as a repeatable script, with today's numbers as the baseline.
2. **A storage map and a durability answer.** Every database, store, key and cache, what it holds, its owner module and its size on a real workspace; whether the browser keeps the data (`navigator.storage.persisted()` on iPhone Safari, desktop Safari, Chrome and Firefox); and whether Blobs in IndexedDB survive on the real iOS Simulator, settling the contradiction above.
3. **A map of the boot path.** Every mechanism from page open to first edit, including every storage key, database and cache the Studio reads on the way and which module owns it, what each one does, what breaks if it is removed (a reverse-dependency check), and which pairs do the same job. Produced with the additive trio (`seam-census`, `blast-radius`, `contradictions`, `engineering/orchestration.md`), each claim with a file and line.
4. **A design note** in `engineering/decisions/`: the simplest boot path that still meets the product's requirements, each current mechanism marked keep, merge or delete with the measured reason. Put to the owner before any code changes (CLAUDE.md, "Design-before-code").
5. **Then cuts in measured steps**, each its own PR with before and after numbers from step 1 (HARD RULE #19). Not part of this issue's done: each cut gets its own issue once the note is agreed.
