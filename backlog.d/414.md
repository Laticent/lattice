# refactor(website): consolidate the per-surface theme/palette dropdowns onto one shared control

## Summary

The theme/palette dropdown is implemented **three different ways** across docs-site surfaces instead of sharing one presentational control. Consolidate the widget (look, option rendering, a11y) while keeping each surface's distinct behaviour.

### Evidence (current state)

| Surface | Control today | What selecting does |
|---|---|---|
| Docs Header | `PaletteControls` (shared) — native `<select>` + moon toggle | sets the **site** palette → `localStorage` (`lattice-docs-palette`), `site-chrome.ts` |
| Drawing Board | its own Radix `<Select>` in `DrawingBoardTopbar.tsx` | writes the **deck's** `theme:` front matter (`__dbChrome.applyTheme`) |
| Workbench Theme Studio | native `<select>` populated via `innerHTML` in `theme-studio.js` | picks the theme being **edited** |

### What's actually wrong (and not)

- **Not** the worst case: the palette *list* is largely single-sourced already (Header derives it from the generated tokens' `data-palette` keys; others receive it via props / `theme-fetch.ts`) — theme names are **not** copy-pasted in three places.
- **The defect**: the *control widget* is triplicated (Radix Select vs. two native `<select>`s), and there's already a shared `PaletteControls` that the Drawing Board and Workbench bypass. The visual affordance, option rendering, and a11y should be one component.
- **Legit constraint to respect**: the three have genuinely different behaviours and state targets, and `theme-studio.js` populates options via `innerHTML` (a Radix `<Select>` "cannot model" that per its own code comment). So the fix is a **shared presentational control wired per surface**, not one component that hard-codes one behaviour.

## Swimlane

`CLAUDE.md` HARD RULE #15 (reuse — tooling AND UI) + `engineering/development.md` (docs-site). The shared layer to extend: `docs/src/components/ui/select.tsx`, `docs/src/components/site/PaletteControls.tsx`, `docs/src/lib/{site-chrome,theme-fetch}.ts`.
