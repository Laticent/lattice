- `engineering/decisions/2026-09-02-nightly-liveness.md` measures whether the nightly family can report that it **stopped running**, and the measurement changed the proposed design twice. All seven scheduled workflows are alive — each ran on schedule on 2026-09-01, median gap 24.0h across 161 scheduled runs — but the observed **maximum** gap is 34.7h, so the proposed 36h threshold carried 1.3h of headroom and would have fired on ordinary GitHub cron drift; 48h is the defensible number. And all seven hit that maximum on the **same night**, so the failure such an alarm sees most often is correlated: one job and one rolling issue, never one alarm per workflow. The note also records why "did a run appear" is not enough — a startup failure and a parked run both leave a run record having executed nothing — so the probe must require a `schedule` event that actually produced jobs. Wiring is left for a decision, since adding a scheduled job is the CI-contract change reserved for the repo owner.
