- **`CHROME_PATH` now actually selects the browser the renderer launches.** It never did: `detectChromeExecutable()` read `PUPPETEER_EXECUTABLE_PATH`, then puppeteer's cache, then `which` — while the SessionStart hook, `AGENTS.md`, `engineering/gotchas/ci.md`, `design/skills/deck.md`, `README.md`, `engineering/pipeline.md` and `test/benchmark/engine-bench.mjs` all set or documented `CHROME_PATH` as the way to fix "no browser". Measured both directions: `CHROME_PATH=/nonexistent/chrome` rendered a deck fine, and with the puppeteer cache made undiscoverable a *correct* `CHROME_PATH` failed while `PUPPETEER_EXECUTABLE_PATH` to the same file rendered. The variable looked load-bearing on every machine that already worked and did nothing on the one machine that did not.
- The two variables are deliberately not symmetric. `PUPPETEER_EXECUTABLE_PATH` stays first and unconditional — a pin that quietly renders on a different browser is worse than one that fails, and `overflow-nightly.yml` pins a specific Chromium precisely so its baseline stays comparable. `CHROME_PATH` is accepted only when it names a file the process may execute, so a stale or decorative value falls through to the cache scan instead of becoming a new render failure. Existence alone is not enough: `/Applications/Google Chrome.app` is a directory, a non-executable file is just as unlaunchable, and both reach puppeteer as `spawn … EACCES`.
- **Every puppeteer-cache resolver in the tree now picks the same build — the newest.** Ten shell sites resolved it with `ls … | head -1`, which picks the *oldest*, while both JavaScript resolvers sort newest-first. That disagreement was harmless only while `CHROME_PATH` was inert; the moment it reached the renderer, a cache holding two builds would have silently moved every sandbox render, the `LATTICE_FULL_PUSH=1` pre-push tier and `npm run bench` onto an older Chromium than the one before. All ten are now `sort -V | tail -1`.
- **Fixed:** `engineering/gotchas/ci.md` blamed browser auto-detection for not knowing about the puppeteer cache. The owned emulator scans that cache itself, so the entry's own "removable when the launcher adds puppeteer-cache discovery" exit had already been met. That half is true of marp-cli, not of the owned engine.
- **Fixed:** `engineering/pipeline.md` and the resolver's own comment described the cache scan as `$HOME/.cache/puppeteer`. It also walks every `/home/<user>/.cache/puppeteer` regardless of `HOME` — which is why overriding `HOME` does not isolate it, and why a test that tried to was a no-op on CI.
