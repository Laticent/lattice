- **A standalone chart SVG now carries its own color definitions.** The export bakes `fill:var(--token)` for every paint that matches a scheme-varying token, so the player can re-theme a chart when its toggle moves. A detached `.svg` file has no host to define those tokens: the `var()` resolved to nothing and the paint fell to the SVG initial, which for `fill` is **black**. Measured on the real files — a `map` export painted **172 of 184 shapes black**, and a `heatmap` export put 3 of its 5 ink stops below WCAG AA (worst `1.98:1`). Both are now 0.
- The exporter resolves every token the file references — through the computed-style bake, through an element's own inline style, and through a presentation attribute like `fill="color-mix(in oklab, var(--chart-cat-1-hue) 88%, …)"` — and writes them into the file's own `<style>` block. The third route is why a first cut still left one token undefined: `map` carries 16 of those and a sweep that read only `[style]` could not see them.
- The collection is opt-in (`collectTokens`), taken by the five call sites that go on to write a file. The three that leave the clone inline in a themed host are byte-identical to before — an earlier cut set the attribute unconditionally, which shipped the deck's fully resolved palette into every exported player as a dead attribute nobody strips (2 copies / 504 bytes on the baseline gallery).
- The fix lands in the shared export kernel, so it covers every chart layout the standalone exporter can lift, not only the two that surfaced it.
