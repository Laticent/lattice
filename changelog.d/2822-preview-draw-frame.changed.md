- The Studio's and the Playground's live previews no longer run function-plot in the page that holds your deck. A plot is drawn in a sandboxed frame (`sandbox="allow-scripts"`, an opaque origin, no network) and the drawing comes back as sanitized markup. The library is fetched and checked against its SHA-256 pin before the frame runs it, and only that frame may `eval`, because the library compiles expressions. The CLI exports and the plain `.html` have no host page and load the library as before, and the Studio's own exports (PDF, PNG, PPTX, Webpage) draw in-page too, so their bytes stay the CLI's. A plot's first draw is at parity with the in-page path (1247 / 1355 ms before, 1292 / 1496 ms after, headless Chromium).
- Mermaid in the Studio's and the Playground's live previews is drawn in a sandboxed frame too, and a first diagram takes about as long as drawing it in the page did, a little less on a first visit. The frame loads Mermaid's own ES-module build by URL (a 28 KB core, then only the chunks a diagram type needs) instead of inlining its 3.1 MB single file, so the page no longer parses 3 MB of HTML or runs a 350 to 500 ms script task. Measured in the real Studio, headless Chromium, 10 interleaved runs each, time from the editor change to the first diagram: median 1414 ms in the page before, 1342 ms in the frame now (ranges 1268 to 1654 and 1082 to 1493); a returning visit is 1112 ms on both; an edit redraw is 652 ms before and 670 to 825 ms now. An earlier CPU trace of one condition (1779 ms to 1366 ms) overstated the gain. The frame's policy names the one directory the modules load from and the engine's font folders, carries no `'unsafe-eval'`, and an import map's `integrity` pins the SHA-256 of every module, which a browser that supports it enforces (a changed module is refused). The ES modules are vendored beside the single file (`lib/plugins/mermaid/vendor/esm/`, pinned by tree hash, refreshed by `npm run vendor:plugins`) and staged under `frames/mermaid/`, which needs CORS: GitHub Pages sends it, the Cloudflare previews read `docs/public/_headers`, and the local servers are configured in `astro.config.mjs`.
- A flowchart's hover tooltip now takes the diagram's own palette (the rule in the diagram's sheet) in the Studio's previews, where the library's own tooltip showed a pale yellow. A link still opens and a click callback stays off at `strict`, as before.
- A Mermaid error in a preview keeps up to six lines (600 characters) of the library's message, the parse position and what was expected; a longer message is cut there, where the in-page library showed all of it.
- If the Mermaid frame cannot load its library (offline, a removed deploy), the preview stops offering Mermaid to the page and the next preview loads the library itself; the frame says so at once instead of after 30 s. The frame does not use the service worker or the HTTP cache, so a returning visitor fetches the modules again on each page load.
- A plugin now chooses the sandboxed preview frame from its manifest: an in-tree plugin declares `draw` (`frame`, `host`, `shim`) and ships `<name>.draw-frame.js` (and optionally `.draw-host.mjs`, `.draw-shim.mjs`); the registry generates the rest. The frame, host, warm-up and preload code name no plugin. Markup from the frame reaches the page through one sink, `ctx.drawInto`.
- A deck's or theme's own embedded fonts (`data:` faces within the size caps, and the engine's font folders) now reach the draw frame, so a diagram's label boxes match the font the slide paints.
- The Studio's deck-wide Mermaid check (what grounds the Architect chat in whether every diagram draws) now sends each diagram to the sandboxed preview frame instead of loading Mermaid into the Studio page, so the page no longer downloads the 857 KB library on the first edit. A frame that cannot answer gives no verdict, as before. The check starts 3 s after you stop typing (it was 0.9 s), so it no longer competes with the visible slide's own draw: on a 20-diagram deck an edit redrew in a median 1.47 s in the frame against 1.51 s in the page, where a 0.9 s start measured about 110 ms slower.
