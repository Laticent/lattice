- **One image library, `@laticent/lastra`, now reads, cleans, resizes and encodes every picture an export or the Studio handles.** Lattice had four header readers, three EXIF orientation parsers and a metadata scrubber only the Studio could use; each is one function in `docs/src/lib/lastra/` now, with no dependencies, the same in Node, a browser and a worker. Exports keep their bytes on the galleries and on a photo deck of PNG, JPEG, turned JPEG and transparent PNG pictures (a PowerPoint's own run-time stamp aside, which never followed `SOURCE_DATE_EPOCH`).
- **A turned photo now exports the way the browser paints it.** Only a deck holding one of these pictures exports different bytes (`examples/lastra-image-reading.md` shows the first three):
  - a JPEG whose EXIF block sits after its frame header (every engine turns it) stays upright in the PDF and is sized upright by the `image` layout;
  - a PNG turned by its `eXIf` chunk (Chromium and Firefox turn it) stays in the PDF's photo instead of being drawn stretched, is sized turned, and is no longer re-encoded squeezed into its stored box;
  - an AVIF photo on an `image` slide is now sized, where it used to fall back to the plain composition;
  - a JPEG whose first EXIF block does not turn it is no longer turned by a later one; a TIFF block with the wrong magic number or an orientation outside 1 to 8 turns nothing; junk or fill bytes between JPEG segments no longer hide a large photo from the export's re-encode.
- **A file whose first bytes only resemble a PNG, JPEG or GIF, and that no browser decodes, is no longer taken for one** by the PDF writer, the CLI's PDF asset reader or the image layout's sizing; they all read the full signature now, as the browsers do.
- **The Studio's cleaned photos keep only the turn a browser applies.** A JPEG with two EXIF blocks, or a PNG with two `eXIf` chunks, used to be stored with an orientation block from each; it now keeps the first block's turn only, so the stored photo paints as the original did.
- **lastra decodes PNG and JPEG itself, in plain JavaScript, with the same answer in Node and every browser.** Baseline and progressive JPEG decode exactly as libjpeg-turbo's C code does (including damaged files and progressive files missing their last scans), PNG of every color type and depth decodes exactly, and the inflate is lastra's own, so a damaged PNG gets one verdict everywhere. Hostile files are refused quickly with a typed reason instead of exhausting memory or time. Nothing uses the decoders for exports yet: that step waits on color management and a real-iPhone memory measurement (`engineering/decisions/2026-11-13-image-library.md` §5, slice 5).
