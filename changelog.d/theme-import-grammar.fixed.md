- **Fixed: a theme that merely MENTIONED another palette in a comment inherited the whole thing.** A header comment reading `/* … like @import 'onyx'; but warmer … */` made the engine splice all 768 KB of `onyx` into a theme that declared no parent — and since comments are stripped afterwards, the rest of that sentence was left behind as live CSS, read as a selector, and swallowed the rule following it (a theme's own `@font-face`, in the case that surfaced). The Theme Studio put a user's free-text description straight into that comment, so any description containing the phrase was enough. Comments are no longer scanned for imports.
- **Fixed: a theme whose parent import is written without quotes composed to an unstyled deck.** The engine store read `@import 'indaco';` and `@import"indaco";` but not the bare `@import indaco;`, so a theme using that form lost its parent and came back as ~2 KB of scaffold instead of the full ~769 KB stylesheet. No shipped palette uses the bare form — a stylesheet handed to `addThemes()` by the Studio, a shared deck, or an external `./engine` consumer could.
- The two remaining places that read a theme's parent out of CSS now share one grammar. The engine store and the `--css` flattener each carried their own regex and had drifted apart — one accepted the bare form and mismatched quotes and mis-read `@import url(…)` as a theme named `url`; the other accepted neither. Both now go through `themeNameImports` / `replaceThemeNameImports` in `lib/theme/chain.mjs`, and a test drives both consumers over the same twenty-two `@import` forms so a future fix cannot reach one and miss the other. Composed output is byte-identical for all 32 shipped palettes across four sizes.
