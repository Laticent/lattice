The Studio's Library now holds photos, and a deck can show one with `asset:<name>`. Measured locally against main with the repo's own script: studio +1075, playground +276, home +268 bytes gz (the studio figure rose from +828 when review hardening added the used-photo delete confirm, the deck-delete cascade and the restore rename pass); CI measured +859, +367 and +365 before the change below, so the declared numbers leave room for gzip spread between builds.
Given back first: the Library-photo render option does not live in `render-engine.ts`, which the home page and the Playground share and which has no Library to serve there. It is a hook only the Studio installs, and the registry, the IndexedDB read and the object-URL code are a dynamic import that loads when a deck names a photo. That took about 90 bytes off each of those two routes.
What remains on the home page and the Playground is the sanitizer's `blob:` allowance in the shared `lib/core/sanitize-slide-html.mjs`, which every preview imports. It keeps a same-origin `blob:` UUID URL as the `src` of an image or media element and nothing wider; without it the sanitizer deletes every Library photo (measured in Chromium). It could be made opt-in so those two routes do not carry it, at the price of a new option on the shared sanitizer; that is left out of this PR and recorded in `followups.d`.
