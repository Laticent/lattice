Surfaces, ink and accent decide how a deck looks. These two groups decide
whether two particular kinds of slide work — a status board and a code
listing — and you set them once.

## Signals — good, careful, bad

Six colors: three inks and three tinted grounds.

```css
--pass: #2D6A3F;   /* the ink */
--warn: #B45309;
--fail: #991B1B;

--pass-bg: …       /* a tint of it, behind a badge */
--warn-bg: …
--fail-bg: …
```

One thing to get right: **warn must not look like fail.** Amber against
red, not two reds. When a slide shows a status board, the difference
between "watch this" and "this is broken" is doing real work, and a reader
seeing them side by side should never have to squint.

## Code — syntax highlighting

Twelve colors for the parts of a code block: comments, keywords, strings,
numbers, function names, and so on.

Two things constrain them. They all sit on `--code-bg`, and every one of
them is **small text a person reads**, so each has to be genuinely legible
against that background — comments and punctuation included. The temptation
to make comments nearly invisible is exactly the mistake: de-emphasis is
about where a color sits relative to the code around it, not about whether
it can be read at all.

## What happens to the ones you skip

The lab above renders a complete code slide from a theme that never
mentions code, because everything a theme omits falls back to the engine's
defaults. That is good while you work and a bad way to ship: a theme that
stops at the colors on these two pages is, in every group it skipped,
quietly wearing the default palette's clothes.

[Ship your theme](/craft/themes/checklist/) lists the full 98, and
[a finished theme](/craft/examples/theme/) shows the hand-written half
whole.
