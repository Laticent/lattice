# 2026-07-02 — Docs site as an installable PWA (runtime-cache service worker)

## Context

The docs site (lattice.style, static Astro + Starlight on GitHub Pages,
Cloudflare Pages previews) had no web-app manifest and no service worker, so
no installability and no offline behavior. We wanted both, cheaply: an app
icon / standalone window, and previously visited pages (docs, Playground,
Studio) surviving a dropped connection.

## Decision

Hand-rolled **runtime-caching** service worker (`docs/public/sw.js`,
~120 lines) + static `site.webmanifest` + PNG icons rasterized from the brand
mark — **no Workbox / `@vite-pwa/astro` dependency, no build-time precache
manifest.**

### Why not vite-plugin-pwa / Workbox precaching?

- **Precaching is wrong for this site's asset profile.** The built site
  carries showcase PDFs, the ~554KB-gz engine bundle, and large playground
  assets. A glob-driven precache either pulls megabytes onto every visitor's
  disk on first visit, or needs a carefully maintained exclude list that rots.
  Runtime caching stores only what a visitor actually uses.
- **No build coupling.** A runtime worker is a plain static file: nothing in
  the Astro build changes, no per-build revision hashes, no "update waiting"
  toast UX to build. A deploy is picked up by the network-first HTML strategy
  with **no SW version bump** — the worker version only changes when the
  caching *strategy* changes.
- **One fewer dependency** in an area (SW lifecycle) where debugging a
  library's generated worker is harder than reading 120 commented lines.

### Strategy summary (details in `sw.js` header)

| Traffic | Strategy |
|---|---|
| Navigations (HTML) | network-first → cache → `/offline/` |
| Versioned assets (`/v/<hash>/…`) | **cache-first** (immutable; see 2026-07-21 update) |
| Other same-origin assets | stale-while-revalidate, FIFO-capped |
| `.pdf` / `.pptx` / `.zip` | never cached (download-manager territory) |
| Google Fonts | stylesheet SWR; `.woff2` cache-first |
| Other cross-origin (OpenRouter, GitHub) | untouched |

### Icons

Manifest icons must be fixed-color rasters, so `tools/make-pwa-icons.js`
bakes the **light** variant of the adaptive mark onto the brand cream
(`#FAF7F2`): 192/512 (`purpose: any`, mark at 80%), a 512 maskable (mark at
66%, inside the 80%-diameter OS mask safe zone), and a 180 `apple-touch-icon`
(iOS ignores manifest icons). Committed; regenerate after any mark change.

### The dev/preview origin trap (why dev actively unregisters)

`astro dev` and `astro preview` share `localhost:4321`, so a worker
registered while verifying a production preview would keep serving
stale-while-revalidate assets under the dev server — including Vite's own
module URLs. `PwaHead.astro` therefore registers only on `import.meta.env.PROD`
builds and **unregisters** on dev builds (the same self-destroying pattern
vite-plugin-pwa uses). Recorded in `engineering/gotchas.md`.

## Consequences

- Installable on Chromium/Android and iOS (add-to-home-screen) — manifest
  validity, icons, and worker control verified in real Chromium; **verified
  on-device 2026-07-02** on an iPhone (Safari add-to-home-screen: correct
  icon, standalone launch, offline pages, branded fallback). Visited
  pages work offline; unvisited navigations get a branded `/offline/`
  fallback (a directory page — Cloudflare Pages 308-redirects `*.html` URLs,
  and a redirected response can't be replayed for a navigation).
- The worker goes live on **any production build's origin** — lattice.style
  AND each Cloudflare PR-preview host. Scope is per-origin, so previews stay
  isolated from prod and from each other; the visible effect is that preview
  URLs are installable/offline-capable too.
- A PWA grants **no extra browser privileges** beyond installability +
  offline; the real installed-app story with filesystem access remains the
  SlideWright Tauri wrapper. This is deliberately the lightweight web-side
  counterpart.
- Cache Storage **ignores `Cache-Control`**, so the worker is conservative
  about what it persists: query-stringed navigations are served but never
  cached (the OpenRouter OAuth callback's `?code=…` must not reach disk).
  Standing constraint: anything secret-shaped ever added to this origin's
  URLs or GET responses needs the same treatment.
- E2E coverage: `docs/e2e/pwa.spec.ts` (manifest linked from all three page
  shells, worker activates on the built site, offline reload served from
  cache, unvisited route gets the fallback).

### Kill switch / recovery

If a broken `sw.js` ever ships: **ship a fixed (or no-op) worker — never
delete the file.** `updateViaCache: 'none'` plus the per-navigation update
check means controlled browsers pick up a replacement worker within a
navigation or two, even while the old worker's fetch handler is misbehaving
(update checks bypass the fetch handler). A 404 at `/sw.js` also unregisters
per spec, but strands the caches on disk — a no-op worker that deletes
`ALL_CACHES` on activate cleans up properly.

## Update 2026-07-21 — versioned assets go cache-first (kill the reload-revalidation storm)

**Genesis.** The original design used ONE strategy for all same-origin assets:
stale-while-revalidate ("serve the cached copy, re-fetch in the background for next
time"). That's a safe default, and at the time the asset set was small and the goal was
*offline + installable*, not reload speed. A storage diagnostic overlay (shipped as a
separate change) later made the cost visible: on a real iOS Safari device, a returning
(normal-browsing) profile carried **114 cached entries** vs **2** in a fresh private
window — and SWR re-fetches + re-`put`s **every one on every reload**, with each `put`
walking the whole cache twice (≈O(N²) key iterations). That per-reload storm (and its
growth over deploys/navigation) is the reload-time discrepancy the user reported ("slower
and slower over time"), while private browsing — with no persistent worker/cache — skips it.

**Change.** The bulk of that cache is content-hashed, across two families: our playground
bundle under `/playground/v/<hash>/` (engine, runtime, theme CSS, KaTeX, Mermaid, via
`asset-version.mjs`) AND Astro's own build chunks under `/_astro/` (the docs pages' JS/CSS
— Astro emits only content-hashed, immutable assets there). A content hash makes the URL
**immutable** — a byte change ships under a *new* path — so revalidating the old path is
provably pointless. Both now serve **cache-first** (like the gstatic `.woff2` already do);
everything else same-origin stays SWR. (The playground family was covered first; extending
to `/_astro/` — the docs-page chunks that dominate a browsing profile's cache — was the
adversarial trio's catch, so the storm is cut on the docs surfaces too, not just the app.)

**Eviction & the cap (corrected after the trio).** The two families are bounded
*differently*, and an earlier draft of this note got it wrong. A `/playground/v/` put runs
`put`'s **version-eviction** (reaps older-hash siblings by suffix) on the miss a new deploy
produces. `/_astro/` names do **not** match the `VERSIONED` regex, so they get **no**
suffix-eviction — they are bounded **only by the ASSETS FIFO cap**. That's still safe: a
new deploy's HTML references new-hash `/_astro/` URLs, so old-deploy orphans are never
re-requested → stay oldest-inserted → FIFO ages them out before current entries. But
cache-first no longer re-`put`s an asset on a *hit*, so it loses the incidental "re-put
moves it young" LRU protection SWR gave the FIFO trim — meaning a heavy single-session
working set could otherwise FIFO-evict an in-use core chunk and break it **offline**. So
the ASSETS cap was raised **300 → 800** to clear one deploy's whole immutable inventory
(~280 `_astro` + ~213 playground ≈ 500) with transitional headroom; the browser's own
storage-pressure eviction is the real backstop.

**No VERSION bump — deliberately.** The bump contract exists to drop caches a strategy
change could make *wrong to serve*; cache-first only changes HOW already-valid immutable
entries are served, so nothing becomes wrong, and a bump would force a needless one-time
full re-download (the very storm we're cutting). The `sw.js` VERSION comment records this
exemption. (The red team argued a one-time bump would also flush any byte-corrupt SWR-era
immutable entry — see the trade below — but that scenario is rare and the bump's cost hits
every returning user, so it's declined in favor of the kill-switch recovery.)

**Trade accepted — no self-heal within a deploy (adversarial trio).** Cache-first never
revalidates, so a hashed asset cached as a corrupt-but-200 body (a CDN/proxy serving wrong
bytes at a hash URL, a truncated write) is served from cache until it's evicted — SWR would
have replaced it on a later reload. Bounded: a new deploy rotates every hash → new path →
clean re-fetch, and the kill switch (ship a no-op worker that deletes `ALL_CACHES` on
activate, below) flushes a poisoned entry. This is inherent to any cache-first strategy
(the fonts already have it); accepted as the cost of removing the storm. `/_astro/` also
rides on an **unenforced Astro invariant** (it emits only immutable files there) — noted in
`sw.js` so the `startsWith('/_astro/')` match is revisited if a future Astro drops a
stable-named file there.

**Verified.** `docs/e2e/pwa.spec.ts` proves it against the built `dist` on the real worker:
a cached asset from **each** family (`/playground/v/` AND `/_astro/`) serves with **zero**
server hits (cache-first), while a non-hashed same-origin asset (the manifest) still fires a
background revalidation hit (SWR) — so the zero is real, not a dead counter. The three PWA
tests (manifest, offline, cache-first) pass together.

**UNVERIFIED (HARD RULE #23):** the *felt* iOS Safari reload improvement. This removes ~N
background re-fetches + O(N²) `put` churn per reload (N = cached immutable assets), a real
CPU/IO/network storm — but the worker still intercepts every request and does one
`caches.match` per asset, an inherent SW cost cache-first does NOT remove, and iOS reload
timing can't be benched from the CI sandbox. Whether the *felt* reload gets meaningfully
faster (storm removed) or barely moves (interception dominates) needs an on-device
before/after — cheaply, the storage overlay's per-reload request count (expect N→~0).
Confirm there after this ships; it's a fast-follow, not a merge gate (the change is
one-line reversible and preserves offline + instant-deploy).

**Adversarial trio (HARD RULE #25).** A change to a live PWA that serves installed users
offline is real blast radius, so the shipped diff got the full trio — red team, Munger
inversion, and an independent checker. It found no blocker (the change is one-line
reversible, offline + instant-deploy preserved) but materially improved it; all folded back:
- **`/_astro/` has no version-eviction, but the code + this doc claimed it did** (all three
  lenses). Corrected here and in `sw.js`; the FIFO-ages-out-orphans reasoning is now stated.
- **The 300 cap was below one deploy's ~500 immutable files, and cache-first drops SWR's
  incidental LRU protection** → a heavy session could FIFO-evict an in-use chunk and break it
  offline (red team + checker). Cap raised 300 → 800.
- **The both-families test could pass without exercising `/_astro/`** (all three) — it picked
  whichever family appeared first. Now asserts cache-first on one asset from *each*.
- **No self-heal for a corrupt-but-200 immutable body** (red team + Munger) and the
  **unenforced `/_astro/`-is-immutable invariant** (Munger + red team) — both now documented
  as accepted trades with their recovery paths.
- **The felt iOS win is unmeasured** (Munger) — kept honestly UNVERIFIED with a named cheap
  on-device fast-follow (the overlay's per-reload request count), not a merge gate.
The checker also confirmed, definitively, that the `/_astro/` addition is **not** a thrash
*regression*: those files were already cached in ASSETS under the same cap and never
version-evicted under SWR, so this diff changes only the fetch strategy — net network
strictly decreases.

### iOS caveats (expected bug-report shapes)

- **Safari tabs only:** WebKit's tracking prevention deletes a site's
  script-writable storage (worker + caches) after ~7 days of Safari use
  without visiting the site, so offline-in-a-tab can quietly lapse. The
  **installed home-screen app is exempt** — it keeps its own usage counter
  and every launch resets it, so its cache persists in practice (storage
  pressure and deleting the app remain the only evictions). Either way the
  cache is disposable: the next online visit re-primes it silently.
- An installed (home-screen) PWA gets **separate storage** from Safari: an
  OpenRouter OAuth round-trip that lands in Safari proper leaves its key in
  storage the installed app can't see — "I connected but it still asks me to
  connect." See the gotchas entry.
- `theme_color` is the fixed light-mode navy; installed-window chrome won't
  track dark mode or the 14 palettes. Cosmetic.
