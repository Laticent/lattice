# Old-browser chart-colour fallback — `@supports` flatten, generated per theme

**Date:** 2026-07-11
**Area:** theming / build / charts

## Symptom

On an LG C4 TV's built-in webOS browser, Lattice charts rendered **solid black**
(pie wedges, choropleth map regions) or **lost their colour entirely** (gantt
bars, journey chips — leaving bare text). Reported with photos of a live deck.

## Root cause

Every chart colour in Lattice resolves through the CSS Color 5 functions
`light-dark()` and/or `color-mix()`, frequently nested — the chart-family kernel
(`lib/components/chart/_chart-family/chart-family.css`), the per-theme `--cat-*`
palette, the journey mood ramp, math's function-plot re-colour. `light-dark()`
shipped in Chromium 123 (Mar 2024); `color-mix()` in Chromium 111. A smart-TV
browser is an old, frozen Chromium fork that predates them.

When such an engine parses a `var()`-driven declaration whose computed value
contains an unsupported function, the **whole declaration is invalid at
computed-value time and is dropped** (CSS Variables §3). SVG `fill`'s initial
value is `black`, so a wedge/region goes black; an HTML `background`/`border`
just vanishes, leaving inherited text. This is a browser-support gap, not a
token or mapping bug.

## Constraints (from the owner)

- **Themes stay exactly as authored** — the `var()`/`light-dark()`/`color-mix()`
  chains remain the single source of truth for modern engines.
- Fix ships at **build time** (no per-instance JS colour computation — that would
  violate `architecture.md`'s "CSS owns appearance; JS only for what CSS can't
  do", and a runtime patch flashes a black chart before it repaints).
- **One mechanism**, scalable to new charts/themes, not fragile.
- Modern render **byte-identical**.

## Decision

A build step (`tools/build-chart-compat-css.js`) generates, **per theme**, a
flat-literal twin of every chart colour inside
`@supports not (color: light-dark(#000, #fff))`. A modern engine evaluates the
guard to *false* and never applies the block (byte-identical render, provable
with `pixel-check` and the inert-block gate); an old engine applies it and gets a
parseable colour. Light values are the default; dark values ride
`@media (prefers-color-scheme: dark)` + `section.dark` — so the fallback flips
per canvas with **no JS and no first-paint flash**. This is the Mermaid
dual-bake philosophy (resolve at build, toggle by scheme) expressed through
`@supports`. The block is appended to each `dist/themes/*.min.css`, the sheet the
exported HTML bundles for browsers (`lib/core/marp-bundle.js`); the PDF path
renders on a modern embedded Chromium and never needed it.

### Why not the runtime

A runtime patch (feature-detect in `lattice-runtime.js`, resolve + repaint) was
genuinely viable — the runtime already patches capability gaps (the geometry
bridge). It was rejected for **the flash**: an old TV browser would paint the
chart black, then a beat later repaint — unacceptable for a boardroom surface.
`@supports` is correct from the first paint. `postcss` (already a dependency)
made the build-time cascade resolution robust, removing the fragility that would
have favoured the runtime.

### How the generator stays non-fragile — three cascade-honest sources

The naive approach (relocate each painter onto its variant selector) mis-targets
cross-element cases (a journey face reads `--mood-color` set on its *parent*
`.journey-mood`). Instead:

1. **Setter flatten.** Every custom-property whose value resolves through a
   modern fn is re-emitted flat on its **own** selector
   (`--mood-color: light-dark(a,b)` → `--mood-color: #hex`). The browser's own
   inheritance feeds every plain-`var()` consumer — cross-element cases resolve
   for free, no DOM-ancestry inference.
2. **Global redefine (chart-scoped).** Theme `:root` tokens read directly by
   chart CSS (`var(--text-heading)`) are redefined flat, scoped to the chart
   section roots, so only chart subtrees are affected.
3. **Painter flatten.** SVG/gradient paint declarations carrying a modern fn are
   re-emitted flat + `!important` (inert on modern since the whole block is;
   enough to override an inline broken paint like a pie wedge's
   `fill:url(#gradient)`). A painter reading a **same-element** local (`--fill-hue`
   set per `[data-s]` on the very element it paints) is joined by appending the
   setter's `[attr]`/`:pseudo` **suffix** to the painter's own selector — robust
   for class- and attribute-keyed variants alike. Cross-element color-mix
   painters (a gantt milestone's child `.gantt-diamond`) are deliberately **not**
   joined (ancestry inference is unreliable and explodes combinatorially); their
   flat token still arrives via source 1, so only a small marker's gradient fill
   degrades.

The recipe stays in the authored CSS; the generator mirrors it flattened via the
shared offline evaluator (`lib/core/resolve-token-expr.js`), so it can't drift.

### Scope

Every chart (all HTML+SVG hybrids) plus **`math`** — the one non-chart component
that re-colours SVG (function-plot traces) through themed tokens. No other
component emits tokenised SVG (`accessibility-textures` uses literal hex; the
checkbox/state mask data-URIs are literal `black` + alpha mask; sample images are
static assets).

### The one degradation

The map's choropleth ramp sets `--mix` **inline per region** (a continuous value,
no CSS rule to flatten), so on old engines it degrades to a single representative
tone (upper-mid intensity) — hue and canvas correct, value-gradation lost. The
**categorical** (highlight) map keeps per-category colour. Agreed as acceptable
"coarse-flat on-brand" degradation for a 5-year-old TV.

## Evaluator fix (shared, beyond charts)

`resolveTokenExpr`'s `color-mix()` parser only handled a *literal* percentage.
The canonical chart-fill gradient writes the ratio as a **token**
(`color-mix(in oklab, var(--hue) var(--pct), var(--bg))`), so `readStop` now
resolves each stop token — the colour *and* the percentage may be `var()`. This
also strengthens the offline Mermaid bridge that shares the evaluator.

## Verification

- **Modern no-regression** — the `@supports not(...)` block is inert on modern
  engines; the render is byte-identical (the coverage gate asserts every rule is
  inside the guard; a chart deck renders unchanged).
- **Completeness** — leak gate: the generated body has zero `light-dark()` /
  `color-mix()` / unresolved colour `var()` across all 32 themes.
- **Coverage** — every black-rendering component (pie, gantt, journey, map,
  quadrant) has a flattened rule.
- **Faithfulness** — `color-parity` (real Chromium `getComputedStyle`) pins the
  baked literal to the browser's used value within Δ≤3, including the
  var()-percentage `color-mix` path.
- **UNVERIFIED** — the actual LG C4. No old-engine browser is reachable from CI
  (HARD RULE #23), so the on-device visual is unverified; correctness rests on
  resolver↔browser parity, not a TV screenshot.
