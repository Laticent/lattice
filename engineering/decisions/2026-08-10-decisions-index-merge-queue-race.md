# The committed decision index vs. the merge queue

**#1547.** Hit live during #1535 — not a defect in that change, a structural race
between a generated-from-everything committed file and a queue that re-tests on a
`main` the PR has never seen.

## 1. The shape

`engineering/decisions/README.md` is generated by `npm run decisions:index` from the
front-matter of **every** note, and it is committed; `build:check` gates its freshness.
A PR that adds a note therefore commits an index that is correct *as of the moment it
was generated* — and stale the instant another decision-doc PR merges ahead of it.

The merge queue is what makes that bite rather than merely annoy. It rebases the PR
onto current `main`, re-runs `ci` on the combined state, and ejects if it goes red.
Per #1547's report of the live incident, #1535 was green on its own head and ejected in
the queue with `unit`, `integration` and `docs-build` all passing — only `lint` failed,
and only on the index. That much is a report of a GitHub run, not something reproducible
from a checkout; what *is* reproduced below is the `build:check` failure it rests on.

It compounds: **an ejection clears the auto-merge flag**, silently — again per the
incident report. The PR then sits green, approved, and un-queued with nothing saying so.
That behavior is now written down in `../workflow.md` § Merging, where someone driving a
PR will actually meet it.

## 2. What actually fails — the issue's diagnosis was one layer off, and so was mine

The issue proposed making the check "order-insensitive". Reproducing the race against
the real corpus (clone `main`, generate two divergent indexes, `git merge-file` the
three-way, then run `--check` on the merged tree) says ordering is **not** the failure.

**What decides the shape of the race is where the two rows insert, and nothing else.**
Measured with `git merge-file` on a synthetic list: two insertions at the *same*
position conflict; two at *any* different positions merge cleanly, even immediately
adjacent ones. Rows sort by date descending then filename, so:

| how the two new rows land | git merge | rows after merge | what `--check` rejected |
|---|---|---|---|
| immediate neighbors, nothing already sorting between them | 1 conflict | — | the conflict markers |
| **anything else** | **clean** | both present, both correct | **only the footer tally** — one short |

The clean case is the dangerous one, it is by far the common one (it takes two notes
being neighbors among ~380 to hit the other), and it is entirely the tally. Both
branches rewrite that single line to the *same* `+1` text, so a three-way merge takes it
with no conflict and the committed count comes out one short.

**Dates do not decide it, and #1535 is the counterexample.** An earlier draft of this
note — and of the code comment, the CHANGELOG entry and two test comments — said
same-date notes conflict and different-date notes merge cleanly. An independent checker
refuted it by replaying the actual incident: `2026-08-10-input-verb-parity.md` and
`2026-08-10-no-safe-default-token-contract.md` **share a date**, and they merged
**cleanly**, failing only on the tally — because `2026-08-10-nightly-invalid-and-silent.md`
sorts between them. The converse fails too: two notes dated a day apart conflict when
nothing sorts between them. The mechanism was right in that draft; the rule over it was
wrong, and it was wrong about the one incident the note exists to explain.

So the fix is two independent halves, closing different cases:

- **deleting the tally** closes the silent case — and closes it *on its own*, because
  with no aggregate line left a cleanly-merged index is byte-canonical again;
- **relaxing row order** closes the conflict case, by making a keep-both-sides
  resolution (HARD RULE #16) legal without a regeneration.

## 3. What shipped

**Write and check are no longer the same assertion.** `render` still emits the
canonical, fully-sorted block — `npm run build` normalizes the file whenever anyone runs
it. `--check` now runs a new `verify()` that holds a PR to the part of the index it is
actually responsible for:

- every note has an entry, rendered **exactly** as its front-matter says (`rowFor` is
  the single definition both `render` and `verify` use, so the two cannot drift into
  disagreeing about what a correct row looks like);
- under the right group heading;
- **exactly once**;
- no row without a note behind it;
- the group headings present are exactly the non-empty groups;
- nothing unrecognized inside the markers — which is what catches an unresolved
  conflict marker, or hand-edited prose someone dropped into a generated block.

It asserts **nothing** about row order.

**The tally is deleted, not forgiven.** An aggregate over every note is the one line two
concurrent PRs cannot both be right about. The alternative — keep it and let `--check`
tolerate a wrong number — ships a stale claim in a committed doc, which is the defect
this repo treats a stale count in a comment as. The rows are the record; the closing
line now says what generated the list and why it carries no totals.

**It fails loud on an empty scan.** With notes on disk and no rows parsed, every
per-note assertion above is vacuously clean — the same guard #1535 added to
`checkNoSafeDefaultTokens`, for the same reason: a gate that cannot fail is also a
claim.

## 4. Verification

The relaxed check was driven against the real corpus, not a fixture, in both directions.
No note counts are quoted — they move with the corpus, and a stale number in a record is
the same defect as a stale number in a comment:

| case | before | after |
|---|---|---|
| concurrent notes, clean 3-way merge (the #1535 state) | `decisions-index STALE` | **OK** |
| conflict resolved by keeping both rows, in merge order | `STALE` | **OK** |
| conflict left **unresolved** | `STALE` | **WRONG** — names all three marker lines |
| a note's OWN row deleted from the index | `STALE` | **WRONG** — `…: no entry in the index` |

An independent checker (HARD RULE #25) replayed the real `#1525 → #1535` rebase from the
actual commits and reproduced the ejection: a clean rebase, zero conflict markers, and a
`build:check` failure whose *only* diff against a fresh regeneration was the tally line.

The unit suite pins the same four plus a drifted summary, a status that moved a row to
the wrong group, a duplicated row, an orphaned row, a deleted footer, a duplicated group
heading, a CRLF-saved README, and the empty-scan guard. Mutating `verify()` to
`return []` fails ten of them. `npm run lint`, `npm test`, `npm run build:check`,
`npm run lint:deck:all` and the integration tier pass.

## 5. What this costs, and what it does not fix

- **A new, mild drift class: an index can pass `--check` and still be rewritten by
  `npm run build`.** That is the direct price of splitting write from check. Concretely:
  a keep-both-sides conflict resolution lands on `main` with two rows out of sort order,
  nothing forces a re-sort, and the next agent running `npm run build` finds an
  unrelated `engineering/decisions/README.md` re-sort in their working tree — to either
  commit as noise or notice and discard. It is self-healing (the first regeneration
  fixes it), bounded (a couple of adjacent rows), and strictly better than the failure
  it replaces (a silent merge-queue ejection), but it is a real cost and not a free win.
- **The conflict case still blocks a merge.** Nothing here makes two notes that sort as
  immediate neighbors merge without a human resolving the conflict. What changed is
  that the resolution no longer has to be a regeneration — and that the *silent* case,
  which is the common one, is gone.
- **`CHANGELOG.md` has the same shape** and is not touched here. It is not
  machine-generated from all of something, so it fails as a *conflict* (visible, and
  already covered by HARD RULE #16's "resolve mechanically and force-with-lease
  silently") rather than as a silent gate failure inside the queue.
- **Nothing sweeps the other committed generated artifacts** for the same
  generated-from-everything property. `dist/` is the obvious next candidate. The
  question worth asking of each is narrow: *does this artifact's freshness check assert
  anything a single PR cannot be responsible for?*
- **The ejection-clears-auto-merge behavior is documented, not automated.** Re-arming
  after an ejection is still a manual step, and still has no notification behind it.
