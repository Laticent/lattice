# The agent kit, and one orphan branch for both kits

**Follow-on from #1701 and the 2026-08-17 uncommit.** Date: 2026-08-30.

## 1. The problem

`2026-08-17-generated-bundles-uncommitted.md` §6 listed this cost the day it
shipped:

> **The agent-facing catalog** (`dist/docs/components.*`, which `CLAUDE.md` tells
> agents to grep) is now built rather than checked out.

It was never paid down. Measured on the tree: `README.md:349`, `CLAUDE.md:734`
and `AGENTS.md:32` all route an agent to `dist/docs/components.pick.md`, and a
fresh checkout does not have it. Separately, the Studio chat's authoring primer —
the single best artifact in the repo for making a model author a correct deck —
had never been reachable from outside the docs site at all.

**What was NOT lost, contrary to the premise this investigation started from:** no
PDF has ever lived in `dist/`. All 365 tracked PDFs are untouched — `.gitignore`
ignores `*.pdf` then negates `examples/`, `exemplars/`, `lib/`, `kit/`, `docs/`,
`themes/` and `test/`.

## 2. The measurement that decided the route, and how it moved twice

The question was where the kit should live. Three answers were written down in
sequence and the first two were wrong; each was corrected by a measurement, not by
an argument.

### 2.1 The transplant test

For every consecutive pair of commits touching a file, take the earlier commit's
**parent** as the base and try to apply the later commit's diff to it — which is
what the merge queue does when it rebases your PR onto a `main` it has never seen.

| File | Transplanted | **Failed** | Rate |
|---|---:|---:|---:|
| `dist/lattice-default.min.css` | 0 | **81** | **100%** |
| `dist/lattice.min.css` | 0 | **77** | **100%** |
| `dist/lattice-runtime.min.js` | 3 | 63 | 95% |
| `dist/docs/components.md` | 26 | 7 | 21% |
| `dist/docs/components.json` | 27 | 6 | 18% |

**The minified bundles failed every single time** — 158 of 158 across the two CSS
files. That is the ejection the uncommit fixed, and it is arithmetic: at ~9.6 KB
per line, any two branches that touch the file touch the same line.

The catalogs are a different animal at 34–161 B/line. Restricted to pairs landing
within 48h — genuinely likely to be open at once — they conflict **6 times in 28**,
and every one of the six was **0–20 hours apart**. The six are all *structural*:
adding a component, or expanding a shared vocabulary.

**So the catalogs were collateral, not cause.** They were swept out because they
shared a directory with a file at 9,823 B/line. §8 of the superseded note had
already said as much: a partial uncommit "would keep `dist/docs/components.pick.md`
greppable for agents."

### 2.2 Why "just commit them to `main`" was still wrong

That finding produced the recommendation *commit the catalogs, let PRs regenerate
them* — supported by a synthetic replay in which two PRs edited different
components and merged clean, and by the fact that
`engineering/decisions/README.md` is a generated aggregate at **26 of 50 commits**,
higher churn than the catalogs, living in `main` today.

The synthetic replay tested the easy case. The real history says 21%, and at ~12
catalog-touching PRs a month that is **2–3 conflicts a month, each one a silent
ejection** — an ejection clears auto-merge and nothing tells you. Rare-and-silent
is worse to live with than frequent-and-obvious. The recommendation was withdrawn.

### 2.3 Density is the enemy, not size

The natural hybrid — commit only the compact `components.pick.md` (105 lines,
17 KB) and mirror the rest — was killed by reconstructing the pick list across 18
historical trees and re-running the merge test:

| | conflicts / triples |
|---|---|
| `components.pick.md` | **2 / 16 (12.5%)** |
| `components.json` | 1 / 16 (6.3%) |

**The compact file conflicts more than the 11,554-line one.** At one line per
component, neighbours sit on adjacent lines and their diff contexts overlap; in the
verbose JSON they are hundreds of lines apart. *Stated as directional, not settled:
this is a reconstruction over 18 of 34 trees, and the control did not reproduce the
real-history rate (6.3% against 21%). It is enough to retire "the pick list is the
safe one" and not enough to rank precisely.*

`components.pick.md` also has **no real track record**: it was introduced
2026-08-17 (#1701), the same day as the uncommit.

## 3. What shipped

An orphan branch, `dist-kits`, carrying both kits:

```
/                README.md + .vscode/settings.json   (staged from tools/kit-branch/root/)
/marp/           the copy-and-go Marp kit            (dist/marp-kit)
/agent/          the LLM agent kit                   (dist/agent-kit)
```

`tools/build-agent-kit.mjs` assembles `dist/agent-kit/` — the six generated
catalogs copied verbatim, plus `lattice-primer.md` and a README index.
`.github/workflows/publish-kits.yml` mirrors both onto the branch and supersedes
`publish-marp-kit.yml`.

**The primer is not a reconstruction.** It calls `buildStudioCatalog`
(`docs/src/lib/studio-catalog.mjs`) and `buildLatticePrimer`
(`docs/src/components/studio/ai/architect-knowledge.js`) — the same two functions
the Studio chat calls — so the published primer and the one the product sends are
the same bytes by construction (HARD RULE #1). `buildStudioCatalog` gained an
optional `root` parameter for this, defaulting to its existing docs-site behavior.
A hand-copied primer would have been a third drifting rendering of one canon, which
is precisely what `2026-07-19-skills-fabricate-authoring-truth.md` found had already
happened twice.

**Push-triggered with a nightly backstop.** Measured over 30 days: **50 pushes to
`main`, 12 of which touch an input.** Path-filtered on-push is therefore both
fresher *and* cheaper than a nightly that reruns 30 times to catch 12 changes. The
nightly stays because a failed push-run would otherwise leave the branch stale until
someone next happened to touch an input; the tree-compare skip makes a redundant
nightly run a no-op.

## 4. The cost of one branch instead of two, and the trap it opens

Consolidating moves the Marp kit from the branch **root** into `marp/`. Its
`.vscode/settings.json` registers themes by **workspace-relative** path
(`./lattice.min.css`), so opening the branch root as a VS Code workspace would give
**unstyled slides with no error** — the exact silent failure the kit's own README
warns about. (`marp.config.cjs` uses `__dirname`, so the CLI path was never at risk.)

The answer is a second, generated `.vscode/settings.json` at the branch root
pointing at `./marp/…`. Both levels now work. A folder *between* the two does not,
and the root README says so.

## 6. Branch protection

Requested by the owner. What GitHub can actually give here is bounded by the fact
that the publisher **force-pushes on every run**, so "require a pull request" would
break it outright — the `sync-backlog` GH013 lesson
(`2026-08-09-automation-under-the-merge-ruleset.md`) in a different costume.

Apply to `refs/heads/dist-kits`:

- **Restrict deletions** — on. Nothing in the publish flow deletes the branch.
- **Restrict updates** — on, so no human or agent pushes it by hand.
- **Bypass**: the **GitHub Actions** integration, so `publish-kits.yml` can still
  force-push.
- **Do NOT** enable "require a pull request" or "require status checks" — either
  blocks the publisher permanently.

**The bypass is the limit of this protection, and it is deliberate.** An
integration bypass is held by *any* workflow with `GITHUB_TOKEN` — the same
objection that got a bypass on `main` rejected in 2026-08-09. It is accepted here
because the blast radius is a derived mirror that republishes on the next push, not
a source branch. If that ever stops being acceptable, the lever is a dedicated
GitHub App as the bypass actor rather than the integration.

## 7. A claim this note corrects

The superseded note's §6 update, and the changelog fragment that shipped with it,
both said the Marp mirror ran "on every push to `main` that touches a real input."
**It did not.** `publish-marp-kit.yml` was `schedule` + `workflow_dispatch` only,
and its own header said so explicitly — "NIGHTLY, BY REQUEST — not push-triggered."
Two documents described a trigger the workflow did not have, and the workflow was
sitting in the same PR.

It is a small error with a familiar shape: the same one §3 of the superseded note
is about. Prose was written from intent rather than from the artifact, and nothing
re-read the artifact. Both are now corrected, and the statement is true of
`publish-kits.yml`.
