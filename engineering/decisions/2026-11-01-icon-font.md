# Icons as a font (2026-11-01)

**Status: in progress, folded into PR #2992.** This note records the owner's decisions of 2026-11-01, the
bake-off that informed them, who owns each piece, and the build order.

## 1. Why

An icon is an inline `<svg>` (`lib/plugins/icons`, `engineering/decisions/2026-09-29-inline-icons.md`). The
PDF writer draws it as vector paths, and Calco stores it in a `.pptx` or `.odp` as a picture: a PNG, plus an
SVG since PR #2992. A picture can be moved but not edited: a recipient cannot recolor it, resize it with the
text around it, or copy it as a character. The owner wants icons to behave the way emoji do: real characters
in a font we embed, so the file carries them and the recipient's app edits them like text.

The owner accepted the caveats up front. A `.pptx` is opened in PowerPoint, an `.odp` in LibreOffice, and a
PDF in any viewer. Copying an icon out of a PDF cannot give anything an operating system font has, because no
system font has our icons. Apps that ignore a file's embedded fonts (LibreOffice reading a `.pptx`, and, by
report rather than test, Google Slides and Keynote) draw the icon's private-use character in a fallback font:
LibreOffice 24.2 shows a stray letter such as "ă" in each tile and pill. That is outside the promise.

## 2. Decisions (the owner, 2026-11-01)

| Question | Decision | Rejected, and why |
|---|---|---|
| Icons as a font at all | Yes | Pictures (today): cannot be edited, and a PNG is baked into the slide |
| How the font is produced | A generator script, run by hand when the icon list changes; its output is committed | Rebuilding on every build, in JavaScript (a less proven stroke-to-outline library, every build pays) or Python (Python joins the CI toolchain) |
| Which icons | The curated set (265 today) | All 5,184 Tabler icons: about 1.5 MB, for icons no deck can name |
| Default drawing | `font` | `svg` default: the editable icon would be opt-in |
| The setting | Two explicit words in the existing `icon:` register, `font` and `svg`, so a deck says what it means | A separate `icon-render:` key; a single `svg` opt-out word with `font` implied |
| Where it applies | The deck's `icon:` line, and a slide's `_class: icon-svg` / `icon-font`, which the shared register mechanism gives every `icon:` word | Deck only (chosen first, then reversed once the code showed blocking a slide needs special-case code in the mechanism every register shares); per icon (`^{database, svg}`), which stays off |
| How the page switches | Each icon carries both forms, its `<svg>` and a one-character glyph, and CSS shows one, as it draws `bare` and `etch` | The renderer writing one form: it never sees the deck's settings, so that needs a new path through markdown, the Studio's live renderer and pills |
| How much font a file carries | The export's Emoji font setting (`fonts: emoji:` and the Studio's Share sheet), as the owner asked at the start | A new `icons:` axis under `fonts:`; following the Text fonts setting |
| Calco | Unchanged in role: it receives the icon font as it receives any font | Teaching Calco what a Lattice icon is |

## 3. The design

### 3.1 Coloring and styling stay where they are

An icon box (`.lat-icon`) paints its tile and edge with `::before`, and its line drawing with
`stroke: currentColor` from `color: var(--icon-line)` (`icons.styles.css`). A glyph takes its color from the
same `color`, as text does. So the tile, edge, corners, the three looks, the eight category colors, the
sizes, every theme and both color modes carry over with no new styling. One font serves every theme and mode.

Line weight is the one thing that moves. `--icon-stroke` is a number today: 2 by default, 1.5 in the `etch`
look, 2.25 in a pill. No theme sets it. A glyph's weight is fixed when the font is built, so the font ships
in those three weights and the plugin picks the nearest. Under `icon: svg`, any weight still works.

### 3.2 Sizes

`sm`, `md` and `lg` scale the icon by 0.85, 1 and 1.6, line weight included, and a glyph scales the same way
with its font size. At 16 px and up, glyph and SVG are the same icon. At 8 to 12 px, Chrome snaps the
glyph's outline to the pixel grid and leaves the SVG soft, so the glyph is the more legible of the two (§5).

### 3.3 The page

The renderer writes the same markup whatever the deck says: the register's words become classes on each
slide, and CSS draws the look (`lib/core/register-factory.js`). So every icon carries both forms inside its
box, the `<svg>` and a one-character glyph span (about 60 bytes), and CSS shows the glyph unless the slide
carries `icon-svg`. A browser fetches a font only when it draws with it, so a deck under `icon: svg` never
loads the icon font. Under `icon: font` the glyph sits in the same box the `<svg>` did. The box keeps its `role="img"` and `aria-label`, and the character is hidden from assistive
technology, so a screen reader still says "Database". The face loads like the deck's other web fonts, only
when the deck draws an icon, and is cut to the icons the deck uses.

**The character is never document text.** The glyph span's `::before` draws it from an attribute
(`<span data-glyph="&#xE019;">`, `content: attr(data-glyph)`), so it is in no text node, as the `<svg>` was
not. The first build put the character in a text node, and it leaked into everything that reads a slide's
text: the LFM conformance adapter read a pill's label as the bucket's codepoint plus "S3", and a slide title,
an outline entry or a copy from the page would have done the same. The exporters read the attribute instead:
Calco's pseudo-text reader already resolves `attr()`, and the PDF reader makes each visible glyph its span's
text for the duration of the read (`materializeIconGlyphs`, `read-slide.mjs`), then hides the drawn `::before`
from the photo like any drawn word.

HARD RULE #29 forbids a typed character doing a drawing's job, because a system font draws it differently on
every surface. This is the rule's own answer, not an exception to it: the glyph is our drawing in our font,
embedded wherever it is drawn, and no system font is ever asked for it.

### 3.4 Exports

Under `icon: font` an icon is drawn in a web font the page loads, so the exporters need little that is new:

- **PDF** (`lib/core/pdf-compose`): the writer already embeds every web font a slide draws with, cut to the
  characters used. The one addition is copy text: each icon carries its name (`ActualText`), so copying it
  gives "database" rather than a private-use character.
- **PowerPoint and ODP** (Calco): an editable file draws each icon as a native outline shape, always (§ 3.6).
  The first build sent the glyph as a run in the icon face instead, with the hosts handing Calco that face; § 3.6
  says why that route was retired, and the hosts no longer carry it.
- **The Emoji font setting decides how much travels:** `exact` (the default) carries the icons the deck uses;
  `used` and `full` carry all 265; `system` carries none, and since no machine has our icons, that export
  draws them as SVG instead: vector paths in the PDF, the SVG picture with its PNG in PowerPoint and ODP.
  The export puts `icon-svg`, the class `icon: svg` stamps, on every slide (`lib/fonts/icon-fallback.js`), and
  the CSS shows the `<svg>`; the exporters read what is visible, so they need no logic of their own to choose.
  The switch rides on the slides, not on the page's `<html>`: the first build set an attribute there, and the
  HTML player, which writes an `<html>` of its own, lost it and drew each glyph in no font (found by the
  checker, below).

### 3.5 Who owns what

| Piece | Owner |
|---|---|
| The icon list, names, aliases, drawings, and the codepoint map (one fixed private-use slot per icon, never reused) | The icons plugin, `lib/plugins/icons` |
| The `font` / `svg` words and their default | The icons plugin's `icon:` register |
| The font files (three weights), the generator, and the check that the font matches the icon list | `lib/fonts`, beside `emoji-faces.js` and `text-faces.js` |
| How much of the font a file carries | The export font setting, `lib/core/font-policy.js` (its `emoji` tier) |
| The PDF | `lib/core/pdf-compose` |
| PowerPoint and ODP | Calco, which stays a general library: it writes text in whatever faces it is given |
| Handing Calco the face, and the `system` fallback | The hosts |
| Shapes in an editable office file (always) | `lib/core/office-icons.js`, read by both hosts |
| Turning an icon's `<svg>` into one native outline shape | Calco's reader (`iconSvgMarkOf`) |

### 3.6 Office files draw icons as shapes (the owner, 2026-11-02)

The owner opened the sign-off PowerPoint on an iPhone (Preview) and in Google Slides. Neither loads a `.pptx`'s
embedded fonts, so each icon's private-use character was drawn in a fallback font: Preview showed empty boxes, and
Google Slides showed whatever picture its own fonts keep at that code point (a fish, a saxophone), off-center in the
tile. Text survives the same fallback because a substituted letter is still the letter; an icon's code point means
nothing outside our font. PDF is unaffected: its fonts always travel and every viewer uses them.

Decisions:

- **An editable PowerPoint or ODP draws each icon as a native outline shape by default**: a freeform built from the
  icon's own paths, stroked with its color and round ends. It draws in every app, stays sharp, and recolors as a
  shape (Shape Outline). Pictures were rejected as settling: they show everywhere but do not edit.
- **Why shapes**: whoever exports rarely controls where the file is opened (an attachment on a phone, an
  import into Google Slides, a chat preview), and a wrong icon on a board slide costs more than an icon that does not
  reflow.
- **No switch (the owner, 2026-11-03).** The first cut let the author keep the font: `office-icons: shapes|font` in
  front matter and `--office-icons`, then, at the owner's ask, one export switch ("Icons for every app", and
  `--no-icon-shapes`). The trio's red team then showed the font never did what the switch promised: an icon glyph sits
  in a box of its own (the glyph is absolutely placed in the icon's box, and Calco writes every absolutely placed text
  as its own frame), laid over the words after it and read last. It never flowed with the text or edited as a letter in
  the sentence, so it bought nothing a shape does not, while every app that ignores embedded fonts lost the icon. The
  owner removed the switch: an editable file always draws its icons as shapes. Shapes are standard DrawingML, which desktop PowerPoint reads natively; no runner here has opened one in PowerPoint (§ 9).

How: each slide takes `icon-svg` (the same switch as `system`), so the page shows the `<svg>`, and Calco's
reader lifts an icon `<svg>` (`.lat-icon-svg`, `.lat-pill-icon`) as one `path` shape (`iconSvgMarkOf`): its content box,
its `preserveAspectRatio` fit, its computed stroke. A drawing that does not read falls back to the SVG picture with its
PNG. A shape cannot sit inside a text box, so the text around an icon is SPLIT there: the sentence becomes one text box
per piece, each where the browser put it, with the icon shape between (reader.ts, SPLIT AT ROOM). The first build held
the icon's room inside one text box with a 1.5 pt space stretched by character spacing; iPhone Preview honored that
spacing only partly, every gap came out about a character short, and the next word slid under the icon ("@ambda" in a
pill). A spacing tweak (no plain space beside the spacer) was tried and rejected by the owner as a trick as bad as baking
the icons into the picture. The split does not depend on how an app treats character spacing (rendered in LibreOffice
with every `spc` stripped, the words still clear the icons); whether iPhone Preview now draws it right is the owner's
check, not verified here. It applies to any room wider than its space by more than 0.6 em (an icon, an inline spark, the
gap between pills, a `::before` marker's box); an inline code chip's padding (about 0.3 em) keeps its spacer and its
sentence stays one box. Not split, and held by the spacer as before: right-to-left text and a line that mixes directions
(its words stop running left to right), justified text and extra `word-spacing` (their wide spaces are the paragraph's
own), a first-line `text-indent`, math (splitting cut an equation into pieces), and a heading. The first piece of a split
paragraph keeps its role, so a footer with a pill is still its footer. In
PowerPoint each piece's box ends at its own text, so it never reaches over the icon after it and takes its clicks;
LibreOffice wraps an .odp text box at its width whatever its style says (`fo:wrap-option` is ignored there), so in an .odp
a piece keeps its usual slack. The cost is editing: the line an icon sits in edits as pieces. A second checker found
the exclusions, the ODP wrap and the lost title on real renders; each has a test that fails without its fix.

The trio's red team (2026-11-03) found three more regressions, each fixed with a test that fails without it: a heading
with an icon left only its first word in the title placeholder ("Our"), so the outline, navigation and a screen reader
named the slide wrong; one icon cut its WHOLE paragraph into one box per line; and an em space or a run of non-breaking
spaces counted as room, so a paragraph with no icon split. Now a heading is never split (it keeps the spacer), only the
line something takes room in is cut (the lines around it stay one box), and a gap is room only when something drawn sits
in it: a picture or drawing, an inline box (an icon, a pill, a spark), or an inline run with a painted background.

The pre-merge grader (2026-11-03) then held that one more defect was on this PR's path: gallery slide 107's pill labels
were hidden in the editable file, in LibreOffice and on Apple alike (also so on `main`). Each row draws its counter
("01") with an in-flow `::before` in its own grid cell. The reader cannot read it as text there, because the row styles
its title with `strong:first-child`, and any stand-in inserted before the title restyles it, which the reader's guard
rightly refuses. Kept in the picture, the counter was given its row's whole box (`pseudoRect` only measured an absolute
pseudo), so the row's pills counted as covered, stayed in the picture, and that picture was written over their labels.
`pseudoRect` now gives an in-flow grid-cell pseudo its cell, from the grid's resolved tracks, without moving anything. A
right-to-left grid counts its columns from the right edge (the checker found the first cut measuring from the left, which
cropped an RTL row's counter from the wrong side and lost it). Where the sum of tracks is not where the cell paints (a
vertical grid, tracks packed anywhere but the start, a transformed host) the reader keeps the host's box, as before.
Across the 120-slide gallery only slide 107 renders differently in LibreOffice, and that slide now shows its labels;
`calco-reader.test.js` pins it (its size test fails without the fix) and pins the right-to-left cell.

iPhone Preview, opened from Files (2026-11-03): with the fonts falling back to Times (it loads no embedded font), every
icon shape that sat inside a group (an icon with its tile, its card or its pill) drew as a speck at the group's corner,
while the icons at the slide's top level drew right. No runner reached that importer, so the owner approved a platform
suite, `office-quicklook` (`tools/office-quicklook.mjs`): macOS Quick Look uses the same Office importer, and it rendered
the same specks (run 41562260174). Two runs then compared ways of writing the same file, each drawn identically by
LibreOffice:

| Variant (Quick Look, runs 41562260174 and 41643684357) | What Apple drew |
|---|---|
| Icons inside their card's group | Specks |
| Each icon in a group of its own, inside the card | Specks |
| Icons inside the group, each path in a 21600-unit space (Office's own preset units) | Specks, worse |
| Every custom shape at the slide's top level | Every icon right |
| Gallery cards with uneven corners or a wrapped accent rule, inside their group | The card's fill and border gone (gallery slide 108: the whole card behind the clause) |

(A fifth variant, groups without a child frame, was dropped before the run: LibreOffice misplaced every shape in it.)

So Apple's importer drops ANY custom geometry inside a group, not only icons, and it did so on `main` already: 64 of the
gallery's 233 card groups, on 22 of 120 slides, hold some. The first fix lifted only icon marks out of their cards and
left those cards empty on an iPhone. The owner chose (2026-11-03): **a card that holds any custom geometry is written
loose, in the order it paints, with no group; a card of presets alone stays a group.** Paint order is unchanged, so
every app draws the same picture; the price is that such a card does not move as one in PowerPoint, a reversal of
2026-10-07's "each card grouped with its contents" for those cards only. The ODP writer keeps every card in `draw:g`:
Apple's importers do not open `.odp`.

Found on the way: Calco's arc-to-cubic conversion swapped each cubic's two control points, so every arc drew as a pinched
loop (the database icon's ellipses). Shipped CSS-mask marks had the same defect in every editable PowerPoint and ODP:
`--shape-refresh` (the cycle and state-chart loop), `--mark-question` (a roadmap's unknown state) and `--mark-dot-bold`.
No test pinned them and nobody had looked. Fixed; `icon-font-exports.test.js` checks that the cubics stay on the
ellipse, and the cycle deck's loop mark was rendered and compared with its PDF (it now matches). Also from the checker:
the switch to shapes applies only to an EDITABLE office file (a picture-per-slide file, and the HTML or player written
beside it, keep the font; the command line switches the live page just before Calco reads it), and a stroke a shape
cannot reproduce (translucent, dashed, non-scaling, hidden, a width in percent) keeps the drawing an SVG picture.

## 4. Size

Measured on a test font built from the 265 curated icons (`fontTools`, strokes converted to outlines):

| | Size |
|---|---|
| All 265 icons, one weight | 80 KB TTF, 23 KB woff2 |
| A deck's cut, 5 / 10 / 25 icons, one weight | 2.4 / 3.7 / 8.1 KB (woff2 1.0 / 1.5 / 3.0 KB) |
| The same, all three weights | 7.2 / 11.1 / 24.2 KB |

Most decks use one or two weights (2, and 2.25 for pills). Reusing an icon, or changing theme or color mode,
adds nothing. Today a `.pptx` stores a PNG and an SVG at every placement (about 1 to 13 KB each), and a PDF
repeats an icon's paths at every placement. A font stores each icon once. A PDF with one or two icons, each
used once, may grow by the font's fixed overhead (about 0.8 KB); every larger deck shrinks or holds.

The site pays for the faces in one more place: the Playground's first-paint snapshot (`docs/src/playground/snapshot-cache.js`)
stores the captured slide's CSS for the next cold load, and kept every `@font-face` whole. The three icon faces added 558
units to the default Edit deck's snapshot, which `main` already held at 123,124 against the 122,880 half-cap
`e2e/playground-paint.spec.ts` pins (that spec failed on `main` too, one run in three). The snapshot now drops any face
no element on the captured slide names, which takes out Caveat and Shantell Sans as well: 122,160 units, and 220 gzip
bytes of Playground JavaScript (`docs/route-budget.d/2992-preview-font-origin.md`).

## 5. The bake-off (2026-11-01)

`examples/inline-icons.md` (47 icons on 9 slides: every frame, look and corner, `sm` / `md` / `lg`, inline,
in pills), rendered in Chromium, light and dark. Each icon's `<svg>` was emptied and the glyph drawn inside
it as `<text>` on the same 24-unit grid, so the page placed both identically.

- **Placement:** every glyph within 0.27 px of its SVG (median 0.06 px).
- **Ink:** within 5% (0.986 to 1.051), so shape and line weight match.
- **Sizes:** 19 to 50 px in the deck all match. Rendered alone at 1x density from 8 to 200 px, glyph and
  SVG agree from 16 px up; at 8 to 12 px the glyph is the crisper of the two (§3.2).

**Two errors in the first run, both the harness's or the test font's, both fixed:**

- The first harness laid the glyph over the page at the SVG's on-screen box, which ignores the padding that
  insets a framed tile's drawing. Framed glyphs sat off center; the owner caught it.
- The test font gave every glyph a left side bearing of 0. Chrome trusts the bearing and moves the outline to
  it, so every icon slid left by its own margin: about 1 px framed, 3 to 4 px bare. The generator must
  write each glyph's real `xMin`, and the half-pixel test below pins it.

## 6. Build order (in PR #2992)

1. **Generator and font.** A script outlines the curated drawings and writes three weights, each glyph
   carrying its true side bearing, at the codepoints in a committed map. A `build:check` gate fails when the
   icon list and the font disagree. No new CI tool: the gate compares a stamp, not a rebuild.
2. **The setting.** `font` and `svg` join the `icon:` register: autocomplete, `lint:deck`, `icons.docs.md`.
3. **The page.** Under `font`, the plugin writes the glyph, keeps the label, and loads the cut face.
   Every gallery golden with an icon moves, by sub-pixel amounts; golden-diff lists them for review.
4. **The exports.** PDF copy text; the hosts hand Calco the face; `system` falls back to SVG.
5. **Tests, each shown to fail on the old code:**
   - every glyph within half a pixel of its SVG, per size and look, light and dark;
   - codepoints never move;
   - the default is `font`, and `icon: svg` gives SVG;
   - the PDF embeds the face and copies an icon as its name;
   - PowerPoint and ODP hold a run in the face, with the face embedded;
   - `system` falls back to the SVG picture;
   - the Studio's exports on Chromium, WebKit and Firefox.
6. **Sign-off.** `examples/inline-icons.md`, extended to every frame, look, corner, size and placement, in a
   light theme, a dark theme and an accessibility theme, as PDF, PowerPoint and ODP, with before/after
   slides.

## 7. What the independent checker found (2026-11-02)

A checker bug-hunted the finished diff on the real Studio and the command line. Each defect is fixed in PR
#2992, and each fix carries a test shown to fail on the code before it:

| Found | Cause | Fix |
|---|---|---|
| The Studio's Share → Webpage drew every icon as a wrong letter | The player's font block looked for the glyph character, but the engine writes it as a reference (`&#xE019;`), so no icon face was added | `drawsIconGlyphs` reads the markup, and skips a glyph under an `icon-svg` slide (`lib/fonts/icon-fallback.js`) |
| The HTML player under `system` drew glyphs in no font | The switch was an attribute on `<html>`, which the player rewrites | The `icon-svg` class on every slide, from one helper, in the command line and the Studio |
| The PDF drew each hidden icon `<svg>` at the page's top-left corner | The reader checked `display` on each shape, never on the `<svg>`; a hidden `<svg>`'s shapes compute as displayed, at the identity matrix | The reader skips an `<svg>` with no box, and a shape under a hidden group (`read-slide.mjs`) |
| A pill's glyph took the label's weight, not the 500 face | `--icon-weight` was set on the sibling `<svg>` | Set on the glyph's own box |
| The Studio test's font check passed with no icon face at all | `document.fonts.check` says yes when no face of the family exists | The test looks for a loaded `Lattice Icons` face |

The same pass also closed two smaller gaps. A KaTeX sheet on another origin replaced the site's origin in the
preview's `font-src`; now both are listed. A deck under `icon: svg` carried the icon font into its page and its
`.html`, though it draws no glyph; now it carries none.

## 8. Hinting: tried, not adopted (2026-11-02)

Hinting adds instructions that snap a glyph's outline to the pixel grid at small sizes. `ttfautohint` (symbol mode, the
only mode that accepts a font with no letters) hinted the 400 face. Each of the 265 glyphs was then rendered through
FreeType at 8 to 20 px and compared with the same glyph drawn at 16 times the size and scaled down (the ideal soft
rendering):

| Size | Error vs the ideal, unhinted | Hinted |
|---|---|---|
| 8 px | 0.71 | 0.70 |
| 10 px | 0.35 | 0.31 |
| 12 px | 0.42 | 0.33 |
| 16 px | 0.31 | 0.33 |
| 20 px | 0.28 | 0.23 |

The hinted glyphs are a little crisper at 10 to 12 px, but they lose small details: at 10 px the server icon's two
dots disappear. Each face grows from 81 KB to 114 KB before compression (41%). The renderers where hinting matters
most, PowerPoint and Acrobat on Windows, cannot be reached here, so the gain is unproven where it counts. The faces
stay unhinted. If a sign-off on Windows shows soft icons
at small sizes, the build step is `ttfautohint(symbol=True)`, one line in `tools/icon-font/build.py`.
