# Specs at 1.0: what is core, how they extend, and how they stay SOLID (2026-11-27)

**Status:** proposed. Nothing in `spec/` changes until the owner answers the ❓ card (§6). Written by the 📜 Spec desk
against `main` at `90a387d4`.

**The owner's order (2026-11-27, in the command center):** "LFM, LTT, etc and all our specs need a desk. These specs
should be version 1.0 on release. we also need to make sure they are up to date with how we have evolved. we have added
@meta and @say and ext. I don't know if these should be part of the spec. once these specs go out the door they are
really hard to change and i want to make sure they have what we need to say but are also designed for extensibility.
they live up to SOLID principles."

## 1. The answer

1. **Ship one document per spec, each at 1.0.** LFM is the hard case: `main` has a ratified LFM 1.0 (2026-10-08), a 1.1
   draft and a 2.0 draft, and the engine already does what the 2.0 draft says. No outside implementation exists (the
   owner: "we are not GA"), so the cheapest honest path is to **re-issue LFM 1.0** as one consolidated document that
   describes the engine at release, and record the October text as a pre-release draft in its history. Shipping
   "LFM 2.0" on day one tells every reader that a 1.0 existed that they should care about.
2. **`@meta{…}` and the four notes are LFM core.** After the cut (meta slice E), a `@meta` record is the only way a
   slide names its layout, so a reader that skips it cannot find the slide's structure. The four notes carry a privacy
   promise (a comment that is not a note never reaches a public channel), and a promise is only worth something if
   every conforming reader keeps it. What is core is the **envelope**: the grammar of a record and of a named note, and
   the rule for what a reader does with a name or field it does not know. The **vocabulary** (which fields a record
   takes, which values a register takes) is not core prose.
3. **Vocabulary moves out of the core prose into generated registries.** LFM 1.1 §2.3 lists about 35 registers and
   their every value by hand, and two of them (`marks:`, `cover:`) are being renamed this week. A table like that in a
   frozen document either blocks every rename or goes stale on the next one. The core says how a register behaves (one
   word per axis, case-blind, an unknown word changes nothing, an L2 tool reports it); the registry, generated from
   `lib/core/deck-settings.js` the way `grammar.json` is generated from the manifests, says which registers exist. A
   rename is then a registry change with a `key-renamed` row, not a spec edit.
4. **One extensibility model, shared by every spec** (§4): a closed core, named profiles a reader opts into,
   namespaced extension keys, must-ignore-and-preserve for what a reader does not know, an optional version
   declaration, and the LTT rule for what a minor or major version may change.
5. **LPM stays a draft at release.** Its own text says it is 0.x "until Mermaid and the chart family run on it", and
   it covers in-tree plugins only. Freezing it at 1.0 now would freeze the part we know is still moving.

### 2.1 Where the published specs disagree with the engine

**LFM 1.0 (the one on the site).**

- **§3.5 Speaker notes is wrong today.** It says any plain comment is a speaker note. Since #3351 (2026-11-21) the
  engine reads only `@note{…}`, `@say{…}`, `@alt{…}` and `@handout{…}`; a plain comment goes nowhere. The repo's own
  `spec/conformance/lfm/four-notes` case already tests the new rule, against a spec that says the old one.
- **No `@meta` at all.** The record grammar (`<!-- @meta{layout=…, footer="…"} -->`, record note §4 and §15) is in no
  spec. After slice E it is the only way to set `_class`, so §2.1 (`<!-- _class: x -->`), the Appendix A example and
  the `class-directive` case all describe a form the engine will no longer read.
- **§2.3 says three keys** (`mode`, `finish`, `logo`) are the whole LFM front-matter surface. The engine reads 110
  (`front-matter.schema.json`), and the 1.1 draft specifies about 40.
- **`paginate:`** appears as a Marpit key the deck uses (§2.3, Appendix A). The engine reads `pagination:` and reports
  `paginate` as `key-renamed` (1.1 §2.3).
- **§7 ties the spec's version to the vocabulary**: "Minor — adding … a component." Every new component would then be
  a spec release, which is the opposite of what §4 says (the vocabulary is generated so it cannot drift).
- **L1 is defined as "produces Lattice layouts"**, which makes the Lattice engine the definition of conformance. A
  second implementation cannot be conformant without being Lattice.
- **No version declaration.** A deck cannot say which LFM it was written for, so a 1.0 reader has no way to tell a
  2.x deck from a broken one.

**LFM 1.1 draft.** Up to date on registers, `pagination`, `_lens` and the inline notation, but:

- still lists `marks:` (splitting into `chart-finish:` and `color-intensity:`, #3510) and `cover:` (becoming
  `cover-layout:`, #3517). Both PRs are **drafts with no engine code committed** as of 2026-11-27;
- §3.5 is the old plain-comment rule (the 2.0 draft replaces it);
- §2.4 `_lens` is a directive comment, which slice E retires in favor of a record field
  (`followups.d/3426-p2-lente-lens-writer-to-meta.md`);
- no `@meta`.

**LFM 2.0 draft.** Correct on the four notes; it defers the record ("land here as they are decided") and is written
as a delta, so no reader can use it alone.

**Diagnostics (1.1 draft, on the site).** Already describes `@meta` (§3.11) and the note rules (§3.5), so it is ahead
of LFM. Gaps: no JSON schema for the finding object; no version field on a finding or a report; `classToken` is
required and named after `_class`, which after the cut is a record field; the rule registry mixes core rules with
rules that belong to profiles (charts, the review tier, the CLI's narration pass), so a linter that implements only
the core has no way to say so. It also calls itself 1.1 while LFM, its parent, is 1.0.

**LTT 1.0.** The healthiest of the set: a closed core, "a reader of any 1.x MUST read every 1.y file, ignoring the
fields it does not know outside the core, and MUST refuse a file whose major version it does not know". It is the
model §4 generalizes. Gaps: the schema's `$id` is under `lattice.style`, its conformance cases live under `docs/`
rather than `spec/conformance/`, and three cases is thin for a 1.0 (none for a refused major, an unknown field, or a
stale segment).

**THEME 1.0 and LATTICE-FILE 1.0.** Both drafts that waited on the owner's sign-off since October; both have a
version rule (LATTICE-FILE's "add an optional field: same version; rename or remove: new version" matches LTT).
THEME names 118 tokens in the spec text, which has the same freezing problem as LFM's register table: it was amended
once already, before sign-off, when the `--hljs-*` tokens were renamed.

**LPM.** 0.13-draft, in-tree plugins only, and says so. Not a 1.0 candidate (§1.5).

**Segno.** LFM 1.1 §3.6 and the record grammar both ride Segno's notation, but Segno has no stated version and no
spec document, only its README and `spec.ts`. A third party cannot implement `@meta` without it. The Segno desk owns
its grammar.

**Front-matter schema.** `"additionalProperties": false`, so it rejects the host application keys (`title:` aside)
that LFM says a conforming renderer MUST ignore, and any extension key. It still lists retired keys (`paginate`,
`say`, `captions`, `marks`, `cover`, `guards`) beside their replacements, with no `deprecated` marker, and states no
version.

## 3. Core, profile or extension: one ruling per construct

The test: **a construct is core when a reader that ignores it gets the document wrong in a way a user would call
broken or unsafe.** Otherwise it is a profile (a named, versioned bundle a reader opts into) or an extension
(a namespaced key someone outside the spec defines).

| Construct | Ruling | Why |
|---|---|---|
| CommonMark + GFM base, slide separators, `split:` | **Core** | the slide model |
| Graceful degradation (L0) | **Core** | the governing rule; unchanged |
| `@meta{…}` record: grammar, scopes (deck, range, slide), the rule for an unknown field | **Core** | after slice E it is the only way to name a slide's layout |
| The field vocabulary of a record (`layout`, `footer`, `finish`, …) | **Registry**, generated | it grows with every component and register |
| The four notes, `@note` `@say` `@alt` `@handout`: grammar, names, audience, "a non-note reaches no channel" | **Core** | a privacy promise is only as good as the weakest reader |
| How `@say` is voiced, timed and captioned | **Timing profile** (LTT) | a reader that never speaks has nothing to do |
| `_class` component and modifier tokens, the card grammar, state markers | **Core grammar, registry vocabulary** | a reader must parse them; the names grow |
| Front-matter register *behavior* (case-blind words, one per axis, unknown word is inert, preserved on export) | **Core** | one rule for every register |
| The registers themselves (`mode`, `finish`, `chart-finish`, `cover-layout`, …) | **Presentation profile, registry** | they style a rendering; a reader that only extracts text needs none |
| Delivery keys (`pace`, `delivery`, `greeting`, `closing`) | **Timing profile** | they change no pixel |
| Inline notation (pills, sparks, icons; 1.1 §3.6) | **Notation profile** | degrades to a readable code span; a text reader can skip it |
| `_lens` / lens record field | **Lens profile** | an audience filter, not structure |
| Fenced sub-languages (`mermaid`, charts, `anima`, `math`) | **Core rule, registry list** | the rule (an unknown fence stays a code block) is core; the list grows |
| Diagnostics | **Its own spec**, with core and per-profile rule sets | a reader need not lint |
| Plugins (LPM) | **Separate draft**, not LFM | how the Lattice engine is extended is not what a document means |

**`@meta` and `@say` specifically.** The owner asked whether they belong. Recommendation: the `@meta` record and all
four note names are core, because both were built to replace something already in core (directive comments, plain-
comment notes) and leaving them out would make core describe a language the engine no longer reads. What is left
out of core is everything that grows: the record's field list and `@say`'s delivery.

## 4. The shared extensibility model

Every spec adopts the same seven rules, stated once in a short shared section (proposed: `spec/README.md` §Rules
every spec follows, normative, cited by each spec).

1. **A closed core per spec.** The core changes only in a new major version. This is LTT's rule today.
2. **Profiles.** A profile is a named, separately versioned part a reader opts into: LFM Core, Presentation,
   Notation, Lens, Timing (LTT), Diagnostics. A reader states what it implements: "LFM 1.0 Core + Diagnostics 1.0".
   This replaces L1 "produces Lattice layouts" (§2.1) with something a second implementation can claim.
3. **Registries for vocabulary.** Components, modifiers, record fields, registers and their words, fences, rule IDs
   and theme tokens live in generated JSON registries with a version and, per entry, `since` and `deprecated`
   (with its replacement). Adding an entry is a registry minor; removing one is a registry major. The spec cites the
   registry and never copies it.
4. **Namespaced extension keys.** Unprefixed lowercase names are reserved for the spec and its registries. Anyone
   else names a front-matter key, a record field, a note or a rule ID with a namespace: `acme.tally:` in front
   matter, `acme.tally=3` in a record, `@acme.recap{…}` as a note, `acme/some-rule` as a rule ID. The exact
   separator must pass Segno's grammar; the Segno desk owns that answer (§7).
5. **Unknown things: ignore when rendering, preserve when writing, report when linting.** A renderer that meets a
   key, field, register word, note name or fence it does not know MUST NOT change the render because of it, and MUST
   NOT show it (an unknown note stays private). A writer (an editor, an export, a migrate tool) MUST keep it
   byte for byte. An L2 tool SHOULD report it (`unknown-key`, warning) unless it is namespaced. A misspelled core key
   still warns, as today.
6. **An optional version declaration.** A deck MAY say `lfm: 1.0` in front matter, and a `.lattice` manifest, an LTT
   file and a theme manifest already carry one. Absent means the earliest 1.x. A reader MUST refuse, with a message
   that a newer reader is needed, a major it does not know; it MUST read any minor of a major it knows.
7. **What a version may change** (LTT's rule, generalized): a patch clarifies; a minor adds an optional construct, a
   profile or a registry entry; a major changes the core, removes something, or makes an optional thing required.
   Every construct still needs its degradation row (LFM §5).

## 5. SOLID, concretely

The owner means the five principles as design properties of a set of documents, not of classes. Each maps to a rule
above and to a test a reviewer can apply.

| Principle | What it means for these specs | Where it lives | Test |
|---|---|---|---|
| **Single responsibility** | One spec, one question. LFM: what a deck means. LTT: when things happen. Diagnostics: what a finding looks like. THEME: what a theme supplies. LATTICE-FILE: how a project is packed. LPM: how the engine is extended. | the split in §3 | no spec defines a term another spec owns; today LFM 1.1 §2.3 defines delivery keys that are LTT's business, and diagnostics names `_class` in its required field |
| **Open/closed** | A new component, register, record field or rule lands without editing a spec's core prose. | registries (§4.3), namespaces (§4.4) | the `marks:` split and `cover-layout:` rename change only a registry and add `key-renamed` rows |
| **Liskov (substitutable readers)** | Any conforming reader can replace the reference one for the profiles it claims, and a deck renders or reads the same within those profiles. | conformance cases per profile, in JSON, run by a reference adapter that does not import the engine's internals | the shared cases pass against a second, minimal reader we write for the test (proposed: a ~300-line text-only Core reader in `spec/conformance/` that extracts slides, records and notes) |
| **Interface segregation** | A reader implements only what it needs: a search indexer reads Core; a narrator reads Core + Timing; nobody must implement charts to read notes. | profiles (§4.2) | each profile's cases run alone |
| **Dependency inversion** | Specs depend on abstractions (the registry format, the finding shape, the record grammar), never on Lattice file paths or the engine's behavior. | every "the reference implementation is `lib/…`" becomes informative, never normative | `grep -n 'lib/' spec/*.md` finds paths only in informative notes and the `spec-parts` block |

- **D3. The register tables.** A: core states the register rules; a generated registry lists registers and words.
  B: keep the hand-written tables in the spec. *Pick A:* two renames this week alone. Default A.
- **D4. Unknown keys and the front-matter schema.** A: §4.5 (ignore, preserve, report) and open the schema to
  namespaced keys (`patternProperties`), with retired keys marked `deprecated`. B: keep the schema closed. *Pick A:*
  a closed schema rejects keys the spec says are fine. Default A.
- **D5. A version line in a deck.** A: optional `lfm: 1.0`. B: none; readers detect features. *Pick A:* cheap now,
  impossible to add a meaning to later. Default A.
- **D6. Which specs ship at 1.0.** A: LFM, Diagnostics, LTT, THEME, LATTICE-FILE at 1.0; a Segno notation spec at 1.0
  if the Segno desk can freeze it; LPM stays draft. B: LFM and LTT only. *Pick A.* Default A.

### 7.1 How this fits the 🧠 Agent-native desk's open choices (#3531, trio comment of 2026-11-27)

The two plans were written apart, so this checks them against each other. Neither has been decided.

- **Their D2 (mark agent surfaces experimental in 1.0 and stamp a version on each)** fits §4.3. One line has to be
  drawn so the two do not collide: **LFM 1.0 cites a registry that is stable** (the vocabulary projection, today
  `grammar.json`, with a `version` and per-entry `since` and `deprecated`). The agent catalog `components.json`, the
  `/agents/` pages and the tool names can stay experimental, and no spec cites them as normative. Today LFM 1.0 §4
  cites `components.json` for component names, so the LFM PR changes that pointer.
- **Lint rule IDs that still carry old key names.** Diagnostics 1.0 freezes the *finding shape* and the *registry
  format*. It does not freeze the list of IDs. A renamed rule keeps its old ID as a deprecated alias in the registry,
  so renaming it is a registry minor rather than a break. This works whichever way their D2 is answered.
- **Their D5 (two deck models: Segno's `lib/core/deck-model.mjs` and Lente's planned spine).** No spec depends on
  either one (§5, dependency inversion: the reference implementation is informative). Whichever model is chosen, no
  spec text changes.
