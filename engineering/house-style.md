# House style — how we write

The rules for the words we write **about** the work: chat replies, issues, PR
bodies, commit messages, changelog fragments, code comments, and the
`engineering/` and `design/` docs.

Two neighbors, so you land in the right file:

- **[design/editorial.md](../design/editorial.md)** covers the words **on a
  slide** — headers as sentences, card titles, cadence across a deck. Different
  surface, different rules. If you are writing a deck, go there.
- **`.claude/agents/prose-checker.md`** is the on-demand auditor for prose that
  ships to strangers (landing copy, the docs site, release notes). This file is
  the standing rule; that agent is the spot check.

This is HARD RULE #30's home. Read it here, not from CLAUDE.md's one-line index
entry.

---

## Why this exists

Two failures, both measured, both invisible to the gates we already had.

**British spellings kept arriving.** HARD RULE #21 has a real gate behind it —
170 curated forms, a ratchet, target zero. But it scans **tracked files**, and
the surfaces that drift most are not files: a chat reply, an issue body, a PR
description, a commit message. Measured over the last 300 commits: **21 British
spellings**, every one under a green build.

**Length is a cost, not a courtesy.** A reply that restates the question, lists
the options it already rejected, and closes with a summary of itself spends
tokens and the reader's attention to deliver the same answer. The reader then
has to find the answer inside the reply. Both prices are paid every turn.

## The four rules

### 1. American spellings, everywhere

`color`, `analyze`, `gray`, `license`, `catalog`, `center`, `while`. American
vocabulary too, where the words differ.

This holds on **every** surface, including the ones no gate can see. The
dictionary is `tools/us-english.js` — one list, read by the `build:check`
ratchet and by the commit-msg hook. The hook **warns and does not block**: a
message may legitimately quote British-spelled text, such as an upstream error
string or a dependency's option name, and HARD RULE #14 forbids `--no-verify`
as the escape from a false positive.

A British spelling inside a `camelCase` or `snake_case` identifier is invisible
to the gate. Name those American too.

### 2. Active voice, named actor

Say who does what.

| Instead of | Write |
|---|---|
| The token is resolved at build time. | `build-css.js` resolves the token. |
| It was determined that the lane clips. | The lane clips its last milestone. |
| Changes were made to the fit spine. | I changed the fit spine's measure step. |

Passive voice earns its place only when the actor is genuinely unknown or
genuinely irrelevant. "The PDF is generated by Chromium" is fine. "It was
decided" is not — decided by whom?

### 3. Plain words, and define a term of art on first use

Write for a junior engineer who joined last week. They are smart and they do not
yet know our vocabulary.

| Instead of | Write |
|---|---|
| leverage the existing abstraction | use what is there |
| the mechanism facilitates | it lets you |
| surface the finding | say what you found |
| in order to | to |
| utilize | use |
| performant | fast |

Our own vocabulary is worth spending, but pay for it once. "The **fit spine** —
the pass that shrinks type until a slide's content fits — runs after layout."
Then use "fit spine" freely for the rest of the document.

Two words that hide the actual claim: **"robust"** and **"seamless."** Say what
survives what, or what no longer breaks.

### 4. Concise: lead with the answer

Put the answer in the first sentence. Support it after. Cut anything that
survives deletion without loss.

Delete these on sight:

- **Preambles.** "Great question." "Let me take a look at that." "I'll start by
  understanding the codebase."
- **Restating the question.** They just asked it.
- **A summary of what you just said.** Scrolling up is cheaper than reading it
  twice.
- **Narrated options you did not take.** "I considered A, B, and C." Name a
  discarded option only when the reader needs to know why it lost.
- **Hedges that carry no information.** "It seems that", "arguably",
  "essentially", "it is worth noting that".

There is **no word limit**, and adding one would be the wrong fix — a real
design explanation would get amputated to hit a number, or split across three
replies to dodge it. The test is not length. It is whether every sentence is
load-bearing.

## Per-surface contracts

**Chat reply.** Answer first. Then evidence. Then, only if there is one, the
open question. If you ran something and it failed, say so and paste the output.

**Commit message.** `area(scope): short summary`, imperative, lower case, no
trailing period (HARD RULE #13). The body says what changed and why, not how
hard it was.

**Issue.** A junior engineer should be able to pick it up without asking you
anything. Three things, always:
1. What is wrong or missing, concretely — with the repro or the file:line.
2. Why it matters, in one sentence.
3. The acceptance check: how we will know it is done.

Plus the four axes (`area:` / `type:` / `priority:` / `status:`) and a linked
governing doc, which is what makes a card `status:ready`. See
[workflow.md](workflow.md) § Definition of Ready.

**PR body.** Fill in `.github/pull_request_template.md`. Lead with one or two
plain sentences before the sections. Be explicit about what you did **not**
verify — HARD RULE #23 means an unverified claim is worse than a stated gap.

**Changelog fragment.** Written for someone upgrading who does not know this
repo. Lead with the user-visible effect in bold, then the cause in one or two
sentences. Name the symptom they would have seen.

> - **Fixed: the roadmap lane no longer clips its last milestone.** The lane
>   measured its width before the fit spine had run, so a twelfth milestone
>   landed outside the viewport. It now measures after.

Not: "Refactored lane measurement logic for improved correctness." That tells an
upgrading reader nothing about whether it affects them.

**Engineering doc.** Say what is true now. Put the reasoning next to the rule it
justifies, so the next person can tell a deliberate choice from an accident. A
dated record of how we got here belongs in `engineering/decisions/`, not in the
middle of a reference doc.

**Code comment.** Explain why, not what. The code says what.

## The checklist

Before you send a reply, open an issue, or write a doc:

- [ ] Is the answer in the first sentence?
- [ ] Any sentence I could delete without losing information? Delete it.
- [ ] Every claim: who or what does it? Named?
- [ ] Any term of art used before it was defined?
- [ ] Any American spelling I got wrong?
- [ ] Would a junior engineer who joined last week follow this?
- [ ] Any "verified" that names no surface and carries no artifact? (HARD RULE #23)

## What is enforced, and what is not

| Surface | Enforcement |
|---|---|
| Tracked repo text — spelling | **Gated.** `checkUsEnglish` ratchet in `tools/check-ownership.js`, via `build:check`. Exceed-only, target zero. |
| Commit messages — spelling | **Warned, not blocked.** `tools/check-commit-msg.sh` via the commit-msg hook. |
| Chat, issues, PR bodies — spelling | **Discipline.** No gate can reach them. |
| Voice, plain words, concision | **Discipline**, everywhere. |

There is no gate for voice or length, and there is unlikely to ever be a good
one — nothing in the tree can tell a load-bearing sentence from a plausible
filler one. The test a reviewer can actually apply: **point at a paragraph and
ask what it would cost to delete.** If the answer is "nothing," it should not
have shipped.
